# Notes for Claude Code

The full project map and caveats are in `AGENTS.md` (imported above). The ones that bite most often:

- **Maps stay current** (AGENTS.md "Maps stay current"): a key change updates `README.md`, `AGENTS.md`, and `CLAUDE.md` in the same change. A key change is a root directory, a project skill (its README row takes the description from the skill's frontmatter and the command the skill tells you to run; `README.md` lists every root directory except `.git`), a public host, a root `npm` script that is how you run something, or a product surface those files already describe. A bugfix inside an existing module is not one. Edit only the sentences the change made wrong.
- **Repo is split**: `client/` = the game + site pages (everything in AGENTS.md below is relative to it), `server/` = NestJS + Prisma + PostgreSQL API (`docs/backend-architecture.md`: layers, HTTP-contract rules, race-safety, the test pyramid). Run client commands from `client/`; the server needs `npm run db:up` (Docker) for its integration suite and for `npm run server:dev`.
- **Server changes follow the test pyramid – the audit fails otherwise**: a new controller / CQRS handler / service / guard / interceptor / adapter gets its own unit spec (`server/test/unit/**/<file>.spec.ts`), a new Prisma repository its own integration spec (`server/test/integration/**/<file>.integration.spec.ts`), new behaviour an HTTP scenario (`server/test/scenarios/`), a new race a concurrency test. Copy the shape of a neighbour (`test/support/unit-context.ts` wires the application layer on in-memory ports).
- **Server invariants that are easy to break**: everything a wallet does to rides / credits / payments runs in ONE transaction under the player row lock (`findByWalletForUpdate`); time only from `ClockPort`; env only through `EnvService`; controllers only dispatch to the bus; errors are `DomainError`s (never Nest `HttpException`); a schema change needs a migration. `npm run server:integration` uses its own `freightchain_test` database – never point tests at the dev one. All checkouts / worktrees share it: on a branch with other migrations set `TEST_DATABASE_URL=…/freightchain_<branch>_test` (see the `run-tests` skill).
- **Escrowed pools / paid tickets** (AGENTS.md "Escrowed pools", `docs/paid-tickets-status.md`; what is not done / open questions / todo: `docs/escrow-open-items.md` – update it when you close or find something): the money is in the Anchor program (`programs/freightchain-pools`), the server only MIRRORS pools and credits tickets from program events; the crank (`CRANK_SECRET`, `pool:crank`) sends only permissionless steps by the chain clock; program mode is ticket-only (no pay-per-ride fallback); lock order player → pool → tickets; the gas sponsor signs only the exact bytes it built. Never touch the global Solana config / `~/.config/solana/id.json`; no deploy or pool creation without the user (it needs their Phantom).
- **Serve over http** (`client/serve.sh` for the game alone, or `npm run server:dev` – Nest serves `client/` and the API on :3000); `file://` can't load the ES modules (use `node tools/build-standalone.mjs` (in `client/`) → `client/dist/freightchain.html` for a double-clickable build, and rebuild it after changes).
- You can test in a **real browser even without the Chrome extension**: `node tools/e2e-chrome.mjs` (use `PORT=<free port>` if another session may be running it – they share :9333) drives headless Chrome and saves screenshots (read them with the Read tool). Use it after visual/gameplay changes.
  Say plainly what was and wasn't verified – it can't judge "feel" (shake, smoke density…), so tell the user what to eyeball.
- **Production is split over six hosts** (apex = landing + lobby, `ride.*` = game, `api.*` = API, `storybook.*` = `viewer.html`, `whitepaper.*` = `landing/whitepaper.html`, `admin.*` = the admin page + the ONLY host of `/api/admin/*`, behind nginx basic auth; a new page on a new subdomain = its own nginx template + `deploy/scripts/remote/setup.sh` + smoke check, and `hosts.js` must strip the new prefix): client code must reach the API and the other pages through `client/js/hosts.js` (never a bare `/api/…` or `/play.html`) with `credentials: 'include'`; the server's `COOKIE_DOMAIN` / `CORS_ORIGINS` come from the deploy. See AGENTS.md "Split hosts".
- **The landing is `landing/`** (Vite, own `npm test`; full map in AGENTS.md "Landing"): never hard-code `/api/…`, `/play.html` or `/lobby.html` in its JS (use `API_BASE` via `wallet.js`, `GAME_BASE`, `SITE_BASE`, `STORYBOOK_BASE` from `client/js/hosts.js`; the footer links the model viewer that way); keep three.js out of it (its dash cards run `client/js/cockpit`, which must not import the scene); images are WebP via `landing/tools/to-webp.mjs`; the hero video stays off the critical path (`data-src`, loaded idle after `load`). After touching the sign-in, session or redirect run `node landing/tools/e2e-wallet.mjs` against a built server (single origin AND the split-host recipe in its header).
- **The whitepaper is a second page of the landing build** (`landing/whitepaper.html`, `whitepaper.*` in production – AGENTS.md "Landing" → Whitepaper): cab style, no innerHTML, its one request is web vitals to `api.<apex>` (the host still 404s `/api/`), text taken from the `docs/` explainers (chapter 05 is itself the public escrow explainer; `docs/pool-program` is the contract spec); its numbers (tiers, verdict thresholds, stream prices, program counts, prod flags) are asserted against the code by `landing/test/whitepaper.test.js` – change both together, and keep its "program not deployed" status honest. Cross-host links use `data-to` + `hosts.js`.
- **Promo clips / trailers / gifs of the game, and their sound**: use the `gameplay-video` skill (`media/`, AGENTS.md "Promo videos + sound"): spec JSON → real gameplay in headless Chrome on a virtual clock → mp4 ≤ 15 s (with an 8-bit soundtrack when the spec has `audio`) + gif ≤ 20 MB in `media/out/video/<name>/` (+ the sound in `media/out/audio/<name>/`), plus compressed `.min.mp4` / `.min.gif` copies and a ≤ 500 kB `.tiny.gif` (modes: default both · `--video-only` · `--audio-only` · `--remux` · `--add-audio file.mp4` for any mp4 · `--compress`; finished clips are committed; `npm --prefix media test` guards it). Sounds, scores and the sound store (`media/out/audio/_store`): the `game-audio` skill. Render on a real GPU, look at `contact.jpg` and the audio waveforms, and keep the copy to what the landing already claims (devnet, weekly SOL pool, no payout amounts).
- **App icon**: `client/favicon.ico`, `client/icons/*`, `client/manifest.webmanifest` are GENERATED by `design/icons/build-app-icons.mjs` – change the script and rerun, don't edit the PNGs. Every page head must keep the icon links (Phantom shows the site's favicon as the dapp logo). See AGENTS.md "App icon".
- **Deploy lives in `deploy/`** (`npm run deploy`, `deploy:init|status|rollback|stats|…`; docs in `deploy/README.md`; the step-by-step is AGENTS.md "Deploying to production"). **Nothing reaches production unless the user asks for a deploy in their CURRENT message** – not after "commit", "merge", "fix it" or a finished feature, and an earlier "deploy" does not cover later changes. Without asking: `npm run deploy -- --dry-run`, `deploy:status`, the read-only `npm run ops`. Everything that changes the server (`deploy`, `deploy:setup`, `deploy:rollback`, `deploy:backup`, `deploy:smoke` – it signs in a throwaway player –, ssh commands that write) needs that explicit ask. Deploy from the main checkout on a clean, committed `main` that contains everything already live. Never commit `deploy/.env` / `deploy/secrets/`; keep `deploy/.env.example` dummy; never print secrets from `deploy/.env`.
- **Configuration** (`docs/configuration.md`, AGENTS.md "Configuration"): a new server env key = `env.schema.ts` + `server/.env.example` + `deploy/.env.example` + the `app.environment` list in `deploy/docker-compose.prod.yml` (the container ignores keys compose doesn't list); `APP_DOMAIN` / `COOKIE_DOMAIN` / `CORS_ORIGINS` are derived from `DEPLOY_DOMAIN`, don't add them to `deploy/.env`. Read env files by key name only – never print values. Runtime knobs (signup free rides, the daily cap, the offline allowances) are rows in `player.GameSetting`, changed with the signed admin settings API — not env keys.
- **Product analytics** (`docs/analytics/index.html`, AGENTS.md "Product analytics"): capture is on this checkout. PostHog Cloud EU, ingest `https://eu.i.posthog.com`, private board https://eu.posthog.com/project/297915/dashboard/1006663 (empty until tiles exist; events show in Activity). Capture is opt-in: `POSTHOG_ENABLED` must be `1` or `true`, a `phc_` token alone stays off, and `POSTHOG_DISABLED=1` still wins. Local `server/.env` pins `POSTHOG_ENABLED=0` and the local compose file does not run the API, so `npm run server:dev` sends nothing. Production `deploy/.env` sets `POSTHOG_ENABLED=1`. `emitAnalytics` checks the port and skips the event factory when off. Never print or commit `POSTHOG_KEY`. Do not flip `$create_alias` (`distinct_id` = the anon id, `properties.alias` = the wallet) until that open bug is decided. Replays are the verified-play recording, not this. Page speed is one Trends insight on `web_vital` (Total count, breakdown `metric` then `rating`, bar chart of the period, name Page speed) — not five charts, not PostHog's `$web_vitals` page, and not a tile on dashboard 1006663. The five names (TTFB, FCP, LCP, INP, CLS) and how to read the bars are in README "Product analytics" and `docs/analytics/index.html` → "Page speed". Local smoke is `posthog-test`; production ingest is `posthog-prod`. Coverage review is `analytics-review` (three local passes, no production ingest).
- **The sim is not deterministic or server-replayable** (floats, variable `dt`, `Math.random`), unlike what `technical_design_document.html` specifies for production – see AGENTS.md "Prototype vs. the design doc". Don't add more `Math.random()` to gameplay logic without noting it.
- **`RIDE_MIN_SECONDS` (300) is a test value (production 1800); there is no in-game currency (the mock FRT wallet is gone).** The road never ends; a shift *completes* after that time AND `COMPLETE_DIST`. Client-side checks are not security.
- **User-tuned shake values** (`SHAKE_START 0.5`, `SHAKE_MOVING 0.1`, `SHAKE_RPM 0.35`) and `START_ENGINE_OFF = true` are deliberate – leave them alone unless asked.
- Numeric tuning requests are **relative to the current value** ("lower it twice" = halve it, "make it 25% more intense" = ×1.25). Say which constant you changed. Doing that work is the `gameplay-balance` skill (`.claude/skills/gameplay-balance/SKILL.md`, `/gameplay-balance`).
- **The route and the start hour of a ride are the SERVER's** (assigned from the seed at creation, `Ride.route` / `Ride.startHour`, applied by the game; no picker, no night key (N is the phone map), no F2 clock; `lockTheme()` / `lockClock()` on real rides – AGENTS.md "Routes are NOT chosen"). A test that needs a route uses `h().seedFor('siberia')`.
- **Free-ride helpers (tutorial + assist)** (AGENTS.md "Free-ride helpers"): free tier only, stored on the ride (`Ride.tutorial` / `Ride.assist`), chosen by the lobby's two checkboxes (ASSIST is disabled on the HARD level – the server refuses it, 409 `assist_not_allowed`, and the game forces it off); starting a ride with the tutorial on sets `Player.tutorialPassedAt`; assist = hull damage + battery drain ×`CFG.ASSIST` 0.5 (server mirror `ASSIST_HULL_DAMAGE` must stay above the verdict's `PASS_DAMAGE_SHARE`); achievement `on-my-own`. **Three free LEVELS** (AGENTS.md "The free run"; `ride-trip.ts` `FREE_LEVELS`, `POST /api/rides` `level?: 1|2|3`, default 1, the lobby's picker → `freightchain.level`): 1 EASY `free-1` 60 s / 420 m (four lanes, no junctions) · 2 CROSSROADS `free-2` 180 s / 1512 m (junctions, a fork) · 3 HARD `free-3` 600 s / 6720 m (full network, no assist) – shift = `FREE_RIDE_SECONDS` × 1 / 3 / 10; achievements `free-easy` / `free-crossroads` / `free-hard`. The client side is `js/guide.js` (a leaf) + `ui/tutorial.js` / `ui/assist.js` / `cockpit/guide.js` – off, it changes nothing (`npm run trace:diff` identical). `play.html?offline=1` forces both off.
- **Free rides and offline runs** (AGENTS.md "Free rides"): a new wallet starts at `free_on_signup` (default 10). Daily refill stops at `free_rides_daily_max` (default 5) and never takes a surplus away. Both live in `player.GameSetting` and change with a signed admin request, which can also add or remove one wallet's balance. `play.html?offline=1` is the plain free trip, counted per browser fingerprint and request IP. Bare `play.html` stays the prototype.
- **The road is endless and generated** by `js/net/` (patterns → segments/junctions/forks, seeded per ride + its trip's `road`; `roads` orchestrator runs it). A FORK = two mirror-image roads of the same length – one road in (s, d), so the server never needs to know which was taken; the truck commits at 205 m, sample column 15 records the road. There is no `ROUTE_LENGTH`/finish – see AGENTS.md "Road network".
- **The server rebuilds the road and judges on it** (AGENTS.md "Verified play"): `server/src/domain/road` is a port of the layout + the hole roll (`js/net/network.js`, `js/net/obstacles.js`); the server serves the ride's OBSTACLE PLAN (`GET /api/watch/:id/road`), the game (`js/road-plan.js`) and every replay draw those holes, and each batch is measured against them (`world-facts.ts` → `world-checks.ts`: `obstacle-ignored`, `offroad-ignored`, `accel-without-gas`). Touching the generator, `PATTERNS`, a trip's `road` / `holesFrom` (`TRIP_ROADS` / `TRIP_HOLE_FIRST`), `FORK`, `HOLES`, the hole roll, the axles / damage rule in `sim/damage.js` or the off-road rule = change the port in the same commit (`road-drift.spec.ts` runs the game's modules beside it and fails otherwise). A hand-built recording must take the holes' damage (`recording(…, { road: seed })` in tests, `server/scripts/road-damage.mjs` for API bots) or it is rejected. Is a stream honest? the `ride-audit` skill (`bash .claude/skills/ride-audit/run.sh <ride id> [--prod]`).
- **Routes/themes live in `js/themes/<route>/`** (own sun/sky/road/terrain/mountains/props each). Create theme materials only inside `create*()` via `basic()`/`trackMat()` (see AGENTS.md "Themes (routes)"). `node tools/e2e-chrome.mjs` saves a screenshot of every route – look at them after scenery changes.
- **3D objects and the storybook** (model viewer `client/viewer.html`, production `storybook.<apex>`): a visual bug, or a new or changed vehicle, prop, landmark, furniture, gantry or hole, is the `storybook-models` skill (`.claude/skills/storybook-models/SKILL.md`, `/storybook-models`). AGENTS.md "Model viewer" points at it.
- Keep modules **acyclic** and use the shared `view` object for canvas size. Single-sided materials must be tracked (`themes/_shared/mats.js`) or listed in `flipMats()` (`js/world/render.js`) or they break in the mirrors.
- `mesh.position` is read-only – use `.position.set()`.

- **Statistics** (AGENTS.md "Statistics", `docs/statistics.md`): running totals per rider + global in `stats.*`, written by `StatsService` from EVERY path that ends a ride (player row lock first) and from donations – a new ride-ending path or donation source must call it (`stats-hooks.spec.ts` fails otherwise); every started ride that ended counts, not only completed shifts; rides are counted free / paid apart; reads are cached (`CachePort`, Redis via `REDIS_URL` or in-process; production Redis = password `REDIS_PASSWORD` in `deploy/.env`, no published port, internal network – keep it that way); crash counters are client-reported statistics, never judged. Drift: skill `stats-reconcile` (`--fix` only locally; production read-only unless the user asks). Test: `run-tests/e2e.sh stats`.
- **The live board** (AGENTS.md "Live board"): `GET /api/live` = rides with a heartbeat within `HB_TIMEOUT_MS` + `online` (soft, in memory, ≤ 3 ids per address – the pages send `visitor` + `page`), `GET /api/replays` = the history (cursor, filters, `replay`). A ride silent for `HB_TIMEOUT_MS` is ENDED by the stale-ride sweeper (failed · heartbeat lost) – never leave a ride `running` because its tab vanished. A closing page says so at once: the landing / lobby / watch page poll once more with `leave=1` on `pagehide` (`site/presence.js leaveOnClose`), the game tab sends a `sendBeacon` (text/plain – only `/end` parses it, `beaconBodyMiddleware`) and ENDS its ride; a back/forward-cache restore of that tab reloads. After touching any of it run the `live-board-test` skill (`bash .claude/skills/live-board-test/run.sh` = `e2e.sh board close close-split`); `server/scripts/sim-rides.mjs` fills a dev server with fake drivers / visitors / watchers.
- **Live streams / replays** (AGENTS.md "Live streams", explainer `docs/replay-and-donations/index.html`): a replay is the verified-play recording played into `st` on a road rebuilt from seed + route (`st.watch` = no sim, no input, the traffic SIM off – the recorded traffic is drawn instead). The sample row is shared with the verdict – only ever APPEND columns (12 = clock hour, 13 = the `FLAGS` bitmask, 14 = the controls held / pressed – `js/input-bits.js`, the replay's yellow input borders; bits are frozen, append new ones (`map` skips bit 25 = MOUSE), 15 = which road of a fork – the replay follows it); the 2 Hz traffic track rides OUTSIDE the hashed batch text and is dropped, never refused. **Feature flags** `LIVE_CHAT` (all|free|off), `LIVE_DONATIONS` (on|off), `LIVE_FREE_DONATIONS` (on|off), `LIVE_EFFECTS` (all|free|off) – four places like any env key; production defaults chat all, donations on, NO free donations, effects on free rides only; the server enforces them (`LiveAccessService`), the pages read `features`. Paid donations: order → the spectator's devnet SOL transfer to the DRIVER → confirm claims the order once (signature unique) → a NEW feed event; money that moved is never refused (delivered as a tip with the reason). A paid hole's place is the driver game's stamp. Effects keep a sliding 20 s gap under a per-ride advisory lock; mutes and stamps are the owner's, under the player row lock. After touching `client/js/watch.js`, `ui/watch-panel.js`, `ui/live-feed.js`, `live-effects.js`, `telemetry.js`, `sim/traffic.js`, `world/holes.js`, `site/pay.js` or the server's `live` module run the `replay-test` skill (`bash .claude/skills/replay-test/run.sh` – watch, replay, flags) and look at its screenshots.
- **The admin API is its own security zone**: `AdminGuard` takes only the ADMIN session (`fc_admin` from `/api/admin/auth/*`, `AdminTokenPort`) – never the player's `fc_session` – and on a split deployment only `Host` = `admin.<COOKIE_DOMAIN>` (read `headers.host`, never `req.hostname` / `X-Forwarded-Host`); every admin change needs a wallet signature over `POST admin/rides/:id/challenge`'s text (`AdminProofService`). New admin routes: guarded by default (`@AdminPublic()` only for the sign-in), changes signed + audited. Tests: `loginAdmin` (`test/support/client.ts`), `testAdmin` (`test/support/admin-fixtures.ts`), the fake Phantom in `server/scripts/e2e-admin.mjs`. Player-facing explanation: `docs/verified-play/index.html` – update it when the checks change.
- **Garage** (`docs/garage.md`, AGENTS.md "Garage"): the lobby tab with the whole parts catalog (5 slots), collection progress, the REAL cockpit canvas (`site/garage-cab.js`, hover loops) and APPLY (`POST /api/garage/loadout`, all-or-nothing, one transaction → `player.CosmeticEquip`). ## Workflow

1. Make the change in the relevant module (see the layout in AGENTS.md); put new tunables in `js/config.js`. If it is a key change (AGENTS.md "Maps stay current"), update `README.md`, `AGENTS.md`, and `CLAUDE.md` in the same change.
2. Run the verification commands in AGENTS.md ("Verifying changes"): e2e-chrome first, then eslint/esbuild. For behaviour-preserving refactors, `diff` the headless trace before/after.
   Server: `npm run check` (root) AND `npm run server:integration`; after API or flow changes also `server/scripts/e2e-browser.mjs` + `e2e-lobby.mjs` against a running server; after live-stream / replay changes the `replay-test` skill.
3. If you touched visuals, look at the e2e screenshots, then tell the user what to eyeball.
4. Keep answers short: what changed, which constant to tune, what is untested.
5. Stop at the commit (and the merge into `main`, if asked). Do NOT deploy: say the change is ready and that `npm run deploy` would ship it (a `--dry-run` may show the plan). Only when the user asks for the deploy itself, follow AGENTS.md "Deploying to production" step by step and report the release id and the smoke result.
