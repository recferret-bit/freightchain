# Deploying to production – detail

## Deploying to production

The replay worker uses the same production `EnvModule` validation as the API. Its Compose environment sets `TRUST_PROXY: "0"` explicitly because it has no HTTP listener; omitting the key prevents CLI startup in production.

Production = one server (`DEPLOY_HOST` in `infra/deploy/.env`), seven names (`freightchain.fun`, `ride.`, `api.`, `storybook.`, `whitepaper.`, `pitchdeck.`, `admin.`; `www.` only as a 301 to the apex, once its DNS points at the server), Docker app + PostgreSQL behind the host's nginx. Reference: `infra/deploy/README.md`. After the smoke test the deploy pings IndexNow with the sitemap's URLs (`infra/deploy/scripts/indexnow.mjs`; a failure only warns).

**On this machine** (`DEPLOY_HOST` is `localhost`, `127.0.0.1`, or `::1`, or `npm run infra:local` directly): the same nginx templates run in Docker on port 80, HTTP only, apex `freightchain.localhost` (`*.localhost` is loopback). No ssh, no certificate, no production env. Nest stays `npm run server:dev` on :3000 (`infra/deploy/local/dev.env` is sourced first). The entity MCP stays on `127.0.0.1:3100` and is not proxied. `npm run infra:local -- down` stops the edge.

**The rule: nothing is deployed until the user asks for it directly, in their current message** ("deploy", "ship it to production"). Committing, merging, "fix it", a green test run or a finished feature are NOT a request to deploy, and a deploy the user approved earlier does not cover changes made after it. When a change is ready, say it is ready and offer the deploy; then wait.
- **Always allowed** (read-only): `npm run deploy -- --dry-run`, `npm run deploy:status`, `npm run ops -- logs|nginx|query|sql|ps` (the `prod-logs` / `prod-db` skills).
- **Only on that explicit ask** (they change the server): `npm run deploy`, `deploy:setup` (nginx sites, certificates), `deploy:stats -- --fix` (rewrites the live statistics rows; the plain `deploy:stats` report is read-only), `deploy:rollback`, `deploy:backup`, `deploy:smoke` (it signs in a throwaway player = one row in the production database), `deploy:init`, any ssh command that writes. A failed deploy rolls itself back; a *manual* rollback also waits for the user.

**Steps** (from the repo root of the MAIN checkout, never a worktree):
1. Green locally: `npm run check` and `npm run server:integration` (in a worktree with other migrations: `TEST_DATABASE_URL=…_<branch>_test`); after API / flow / admin changes also the real-Chrome e2e (`bash .claude/skills/run-tests/e2e.sh`).
2. Committed and on `main`: the deploy ships `git archive HEAD` of the checkout it runs in – uncommitted changes are not deployed, and a deploy from a commit that lacks what is live **rolls those features back**. Work done in a worktree: fast-forward `main` first (`git merge --ff-only <branch>` in the main checkout). Nothing needs to be pushed.
3. `npm run deploy -- --dry-run` – the checks, the production env validated by the server's own schema, ssh, and the plan: the commit, the release serving now, whether first-time setup will run (= nginx sites / the certificate change). Show the user the plan. The free levels' lengths are `FREE_RIDE_SECONDS` (EASY's) × 1 / 5⁄3 / 5: with the 2026-10-11 levels `infra/deploy/.env` must say `FREE_RIDE_SECONDS=180` (it said 60 for the first round) – check by key without printing the file: `grep -qx 'FREE_RIDE_SECONDS=180' infra/deploy/.env && echo ok`; change it together with that deploy, never before (the old code would run 3 / 9 / 30 min). The same check refuses the deploy when `strictModeIssues` fails. A missing live-stream key is judged by the schema default, not by the compose fallback. The keys, the 2026-10-23 production file, and what each change does are in `infra/deploy/README.md` → "Production env gate".
4. On the user's go: `npm run deploy` (it asks to confirm; `-y` only when the user said to go ahead without asking). Upload of env + code → image build (the landing's tests gate it) → **database backup** → migrations → container swap → health check (automatic rollback on failure) → the smoke test against the public URLs (also the `admin.*` password and isolation).
5. Verify and report: the release id it printed, the smoke result, `npm run ops -- logs --since 10m --errors`, after a migration `npm run ops -- query migrations`.

**Environment** (`infra/deploy/.env`, gitignored, in the main checkout; `DEPLOY_ENV_FILE=<path>` points the scripts at it from elsewhere): `DEPLOY_*` keys stay local (host, domain, the admin site's basic-auth `DEPLOY_ADMIN_USER` / `DEPLOY_ADMIN_PASSWORD` – only an apr1 hash is uploaded), everything else becomes the app's env; `APP_*`, `COOKIE_DOMAIN`, `CORS_ORIGINS` are derived. A new setting = the server's env schema (`backend/server/src/infrastructure/config/env.schema.ts`) + a dummy line in `infra/deploy/.env.example` (+ `infra/deploy/scripts/init-env.mjs` if it is a generated secret); the real value goes into `infra/deploy/.env` only when the user asked for it, and secrets are never printed in the chat or in commits. `VERDICT_ENFORCE` defaults to shadow mode (`false`) in production.

**Migrations** are forward-only and run in every deploy after the backup; one that drops or rewrites data needs the user's explicit OK before the deploy, separately from the code. **The entity MCP (AI model editor)**: the `mcp` compose service (`infra/deploy/Dockerfile.mcp`, internal `editor` network with the app plus restricted Redis access on `cache`, no published port) is built and started by `release.sh` only when `infra/deploy/.env` has `EDITOR_MCP_TOKEN` (24+ chars; `npm run deploy:init` generates it for a new env file – an existing one needs the line added by hand, with `openssl rand -hex 24`). The AI keys (`ANTHROPIC_API_KEY` …) go in `infra/deploy/.env` only on the user's say-so. **The 3D model API (storybook editor)**: `infra/deploy/nginx/fc-limits.conf` (rate-limit + connection zones, the bundle's microcache) and the `/api/entities/` snippet are written by `remote/setup.sh` on every setup, which also adds the snippet's include to an installed api.<apex> block. The **storybook site file is installed only when ABSENT**. An existing file that has `location ^~ /api/editor/` but no `fc_editor` zone gets that `limit_req` inserted by setup; setup fails if the location is missing, so a vhost from before the editor still needs the hand rewrite below. After the first deploy with the editor, update it BY HAND on the user's go: on the server `sudo cp /etc/nginx/sites-available/freightchain-storybook{,.bak}`, rewrite it from `infra/deploy/nginx/storybook.conf.template` (`sed -e "s/__ROOT__/<apex>/g" -e "s/__PORT__/<app port>/g"`), re-add certbot's TLS block (`sudo certbot --nginx -d storybook.<apex>` reinstalls it), `sudo nginx -t && sudo systemctl reload nginx`; then `npm run deploy:smoke` checks storybook `/api/entities/bundle` = 200 and `/api/editor/me` = 404. The same hand update applies whenever the template changes (it did with the security review of 2026-10-15: `^~` API locations, `/API/` 404, headers on the `.html` location, `frame-ancestors 'none'` / `nosniff`) – the setup-written snippet (`/api/editor/mcp/` 404) updates itself. **New subdomain / nginx change**: an own template + `infra/deploy/scripts/remote/setup.sh` + a smoke check (see `infra/deploy/README.md`); the next deploy runs setup and expands the certificate – call that out in the plan.

The MCP release gate checks its container health (including its Redis connection). Redis counter keys use `noeviction`; the MCP ACL is restricted to `fc:mcp-rl:*` and cannot read application data. Rotating `EDITOR_MCP_TOKEN` must recreate both Redis (its ACL) and MCP, which the compose deployment does.

AI job execution runs in the dedicated `editor-worker` service and can run across worker replicas using the same PostgreSQL queue and Redis rate-limit store. Replicas need identical timeout/provider/signing configuration and synchronized clocks. For the first rollout from the old process-local runner, pause new AI claims (`editor_jobs_parallel = 0`), finish or cancel active jobs, then replace all old app processes before resuming. Do not run the old startup sweeper beside the new queue: old code treats other processes' jobs as orphans. Compose starts one API, the existing replay worker, and (when configured) one AI worker plus MCP. The AI worker uses the server image, no public port, a 1 GB memory limit, and readiness based on recent queue polls. Releases and rollbacks stop the outgoing AI worker, start matching optional services and require MCP + AI-worker health. The API continues to accept queued jobs while the AI worker is stopped.
