# Landing + whitepaper – detail

Agent reference, moved verbatim out of `AGENTS.md` (which keeps only the map and the hard rules and is loaded into every agent session); an "In short" block, where there is one, is a summary. Read the file for a topic before changing it; keep it current like AGENTS.md ("Maps stay current").

## In short

A Vite 7 project, vanilla JS: `npm run landing:dev|build|lint|test` (all in `npm run check`); Nest serves `landing/dist` at `/`.
- Never hard-code `/api/…`, `/play.html` or `/lobby.html` in its JS (`API_BASE` via `wallet.js`, `GAME_BASE`, `SITE_BASE`, `STORYBOOK_BASE` from `client/js/hosts.js`); keep three.js out (its dash cards run `client/js/cockpit`, which must not import the scene); server text only via `textContent` / `el()` (a test forbids `innerHTML`); images WebP via `landing/tools/to-webp.mjs`; the hero video stays off the critical path (`data-src`, loaded idle after `load`). After touching the sign-in, session or redirect run `node landing/tools/e2e-wallet.mjs` (single origin AND the split-host recipe in its header).
- **Whitepaper** (`landing/whitepaper.html`, the second Vite page, host `whitepaper.<apex>`): cab style, no innerHTML, its one request is web vitals to `api.<apex>` (the host 404s `/api/`); text from the `docs/` explainers (chapter 05 is the public escrow explainer); its numbers are asserted against the code by `landing/test/whitepaper.test.js` – change both together, and keep the devnet, not-audited, payouts-off status honest. Cross-host links use `data-to` + `hosts.js`. HTML budget ≤ 27 kB gz.
- **Search + AI crawlers**: every public page keeps its `<link rel="canonical">` / absolute `og:image` (production URLs on purpose), JSON-LD in `<head>` (the whitepaper's `version` / `dateModified` = its header chip), and `landing/public/{robots.txt, sitemap.xml, llms.txt, indexnow-key.txt}` agree with them – `landing/test/seo.test.js` checks all of it. A new public page = canonical + a sitemap `<loc>` + an llms.txt link; a page not for search = `<meta name="robots" content="noindex">` (never a robots.txt Disallow). Detail below.

## Detail

The `/` page: a Vite 7 project (`index.html`, `src/`, `public/media/`, `test/`, `tools/`), 6 chapters (ride · loop · economy · roadmap trip-sheet · go-to-market load board · about) with a live ticker, pool / live / next-up / top-10 boards from the PUBLIC API (no session needed to look) and a four-phase daytime collage.
- **Commands** (root): `npm run landing:dev` (:5173, proxies /api + the other pages to Nest) · `landing:build` → `landing/dist` · `landing:lint` · `landing:test`; all of them are part of `npm run check`. In `landing/`: `npm test`, `npm run media` (re-captures the card posters + sky shots from the game; needs the game served, e.g. `BASE=http://localhost:8765`).
- **Serving**: Nest serves `landing/dist` at `/` in front of `client/` (`LANDING_DIR`, default `../landing/dist`; no build = `/` is the placeholder `client/index.html` + a warning). Hashed `/assets` are `immutable`, `/media` 1 day, pages `no-cache`; text is gzipped (`server/src/app/app.module.ts` `siteRoots`, `infrastructure/http/static-cache.ts`, `compression` in `configure-app.ts`). `deploy/Dockerfile` builds it in its own stage and its tests gate the image.
- **Sign-in + session** (`src/main.js`, uses `client/site/wallet.js`): CONNECT → the injected wallet (Phantom / Solflare) signs the server's challenge → the backend verifies the ed25519 signature and sets the httpOnly `fc_session` cookie (Domain = the apex when `COOKIE_DOMAIN` is set, so landing, lobby, game and API share it) → redirect to `${SITE_BASE}/lobby.html`. Back on `/`, `GET /api/me` shows the wallet chip, "Signed in as …" and turns the CTA into OPEN THE LOBBY. The landing never sees the token. All API calls go through `wallet.js` (`API_BASE`); links to the game use `GAME_BASE` (`ride.<apex>`); the page never hard-codes `/api/…` or `/play.html` in JS. **`node landing/tools/e2e-wallet.mjs`** drives it in real Chrome with a fake Phantom (WebCrypto ed25519; no wallet / rejected / forged signature / success / session recognised / redirect), also against split hosts (see the header of the script: `*.localhost` + `COOKIE_DOMAIN` + `RESOLVE`).
- **Whitepaper** (`whitepaper.html` + `src/whitepaper.{js,css}`, the SECOND page of the same Vite build – `vite.config.js` `build.rollupOptions.input`; production host `whitepaper.<apex>`, locally `/whitepaper.html`): a long read in the landing's cab style – contents rail, abstract + status table, thesis, 02 how to drive (inputs, indicators, lamps, advice, routes), 03 rides + rules of participation, 04 rewards (every reward with a state: LIVE / BUILT / PLANNED; prize figures are proposed defaults, no payout amounts), 05 the escrow program (the one public explainer: money flow, the state machine, the clock timeline, who-can-do-what, guarantees, what it does NOT promise; the landing and the lobby link to `whitepaper.<apex>#onchain`), 06 telemetry + validation, 07 streaming, 08 risks + roadmap + disclaimer (no token, devnet). **No innerHTML. The only request is web vitals** (`reportWebVitals` in `whitepaper.js` → `POST /api/telemetry` on `API_BASE`); the host still 404s `/api/`, and derived `CORS_ORIGINS` includes `https://whitepaper.<apex>`.; its few cross-host links carry `data-to="site|game|storybook"` + `data-path` and `whitepaper.js` resolves them through `hosts.js` (the HTML keeps a same-origin fallback). Copy it from the explainers in `docs/` (current), NOT from the landing's About / Roadmap text. **Numbers are quoted from code and `landing/test/whitepaper.test.js` fails when they drift** (`ride-tier.ts`, `verdict-rules.ts`, `live-rules.ts`, the program IDL's 14 instructions / 12 events / 24 errors, the prod LIVE_* flags): when you change one of those, change the page in the same commit. The status table says the escrow program is on devnet, not audited, with payouts off – update that table and section 05 when that changes. nginx: `deploy/nginx/whitepaper.conf.template` (`/` → `/whitepaper.html`, `/api/` 404); the smoke test looks for the marker `FREIGHT CHAIN · WHITEPAPER`. **Chapter 02's dash cards** (`ol.path` = the nine-step first minute with arrows, two `.cards3` grids = controls on demand + indicators): each `.card3d[data-live]` is drawn by the game's own cockpit code (`dash-live.js`, lazy, `lazy: true` = a card draws once it is near the viewport; no poster images) from `src/wp-scenes.js` (pure: `crop`, `tick(t, g)`, optional `t0` first-frame second, `mark(t)` amber outline, `fit`); `test/wp-scenes.test.js` pins card ⇄ scene, the step order, crops and purity. A new card = markup + a scene; the HTML is close to its 27 kB gz budget, so keep card text short and trim before adding. Budget: CSS of both pages ≤ 14 kB gz, the page's HTML ≤ 27 kB gz (raised from 24 on Oct 9 for the anti-cheat chapter, to 27 on Oct 10 for the free levels / forks / phone map).
- **Hero video** is never on the critical path: `data-src` on `#hero-video` (empty = none, the WebP slideshow is the hero); it is fetched after `load` when idle, not on data-saver / reduced motion / phones, fades in once playing, and a failure keeps the slideshow. The demo dialog video is `preload="none"`.
- **Live dash cards** (`src/dash-live.js`): lazy-loads the game's `client/js/cockpit` (no three.js – keep it that way: `cockpit/*` must not import the scene; the windscreen dust colour lives in `weather.grime`) into ONE hidden canvas; each card keeps its own copy of `st`/`dn`/`disp`/`weather`/`wip`/`radio` + `keyAnim`/`lever` (exported from `cockpit/common.js`) and swaps it in before its draw, then copies its crop. `src/dash-scenes.js` = pure data: crop rect (design px of a 1280×633 cockpit) + `tick(t, g)` script per card. Cards animate only on hover / focus / tap (one still frame otherwise; reduced motion = still). Changing cockpit code can change the cards – look at them (`landing/tools` screenshot pattern, or the e2e-wallet shots). The lights card is the headlights, the cab lamp, HEAT and COLD (`N` is the phone map, not a night button); `npm run media` recaptures its poster from the live cockpit.
- **Media**: only WebP (+ `og.jpg` for link previews); every `<img>` has `width`/`height`/`decoding`; the first hero slide is `fetchpriority="high"`. Add an image with `node landing/tools/to-webp.mjs <files>`; `test/page.test.js` fails on orphan or missing files and on PNG/JPEG.
- **UNDER THE HOOD cards** (chapter 03, `.oc-grid`, `article[data-card]`): five flip cards after the lobby's achievement card – hover, a tap (`.flip`) or Tab onto a link on the back (`:focus-within`) shows the receipt. Not buttons: the back is hidden with opacity, so screen readers read both faces. `chain_card_flipped {card}` once per card per load (a tap, or a 0.6 s hover). Drawings: `public/media/chain/*.svg` (no-JS and reduced-motion picture); `src/chain-scenes.js` (lazy, loaded when the grid is near) swaps each for a 240×124 canvas scene – a ~6 s cycle whose values and timing are re-rolled every round plus random events, drawn only on screen and face up. `test/chain-cards.test.js` runs every scene 90 s on a fake context (no throw, text inside the frame, far more distinct frames than a loop). Copy is checked against the code: Blinks = buy a ticket / open a ride (no tip – tips are the stream's Solana Pay QR); pledges have no stream button yet.
- **Code layout**: `src/format.js` (pure formatters + label tables), `src/dash-scenes.js` (pure), `src/dash-live.js`, `src/chain-scenes.js`, `src/main.js` (DOM + data). Server text goes in with `textContent` / `el()` only (a test forbids `innerHTML`). Class names must not collide with layout classes (`.dot.top` once picked up the sticky `.top` header).
- **Tests** (`npm test`, node:test, no deps): formatters, card scripts (pure, bounds, loops), page integrity (ids, anchors, media, alt/size, a11y, no innerHTML, hero video, sign-in wiring) and the size budget of `dist/` (skipped when there is no build; JS ≤ 55 kB gz incl. the lazy dash and chain-scene chunks, CSS ≤ 14 kB gz, landing HTML ≤ 15 kB gz, no image > 120 kB).

## Search + AI crawlers

The pages are static HTML, so crawlers without JavaScript (most AI crawlers) read the real text; the live numbers are `–` until the API answers (never `0`, an AI summary would quote it).
- **One URL per page**: `https://freightchain.fun/` (landing), `https://whitepaper.freightchain.fun/` (whitepaper), `https://ride.freightchain.fun/play.html` (game, `?watch=` links fold into it; no `og:url` there so a shared watch link keeps its own URL). Written out as production URLs on purpose – a staging copy then points search at production. nginx 301s the duplicates (the `fc-seo` snippet in `deploy/scripts/remote/setup.sh`: `ride.<apex>/` → apex, `<apex>/whitepaper.html` → whitepaper host; `deploy/nginx/www.conf.template`: `www.` → apex).
- **noindex**: `client/lobby.html`, `client/viewer.html` (storybook host), `client/admin.html`. robots.txt blocks only `/api/` – a Disallowed page's noindex is never read.
- **`landing/public/`** (Vite copies it to the root of `dist/`, served on every host): `robots.txt` (all open but `/api/`, AI crawlers named – GPTBot, OAI-SearchBot, ClaudeBot, PerplexityBot, Google-Extended… – and the absolute `Sitemap:` line, which also authorises the sitemap's cross-host URLs), `sitemap.xml` (the three canonical URLs, no `lastmod`), `llms.txt` (summary + links for AI assistants; the same one-line description as the JSON-LD), `indexnow-key.txt` (public by design; `deploy/scripts/indexnow.mjs` pings IndexNow – Bing, Yandex… – after every deploy, `--dry-run` to see what it would send).
- **JSON-LD**: the landing has `Organization` (+ `sameAs` = the X / YouTube / GitHub links the page shows) + `WebSite` + `VideoGame`/`WebApplication` (free offer); the whitepaper a `TechArticle` about that game. Never add an `aggregateRating` or review that does not exist. Validate with Google's Rich Results Test after a change.
- **Budget**: with the JSON-LD the whitepaper is 26.5 of its 27 kB gz (`test/budget.test.js`) – prune before growing it.
- **Outside the repo** (one-time, by hand): Google Search Console **Domain property** (DNS TXT – covers every subdomain), submit the sitemap; Bing Webmaster Tools → import from Search Console; a `www` A record, then `npm run deploy:setup`. Check with `site:freightchain.fun` on Google and Bing, URL Inspection, and a link pasted into X / Discord.

## App icon (browser tab, Phantom / wallet connect, home screen)
Chosen design = **Solana Road** (road to a purple glow, lane marks in the Solana gradient); the other nine candidates incl. **Horizon** stay in `design/icons/` (SVG + 1024 px PNG, `gen.mjs` regenerates them). `node design/icons/build-app-icons.mjs` (needs Chrome + macOS `sips`) writes the shipped set into `client/`: `favicon.ico` (16/32/48), `icons/{icon.svg, icon-192, icon-512, maskable-512, apple-touch-icon, favicon-32}`, `manifest.webmanifest`. Fixed root paths on every host (the apex, `ride.*`; the landing build does not shadow them); every page's `<head>` links them (`landing/index.html`, `client/{lobby,play,viewer}.html`; `landing/test/page.test.js` checks the files exist). **Phantom shows no logo from code: it reads the page's own favicon / apple-touch-icon of the origin you connect from** – so these links are the "wallet logo". Wallets cache the icon; a new one can take a while to appear. To switch design: edit `build-app-icons.mjs`, rerun, commit the output.
