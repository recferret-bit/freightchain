# Money + escrowed pools – detail

Agent reference, moved verbatim out of `AGENTS.md` (which keeps only the map and the hard rules and is loaded into every agent session); an "In short" block, where there is one, is a summary. Read the file for a topic before changing it; keep it current like AGENTS.md ("Maps stay current").

## In short

- One road per competition: a ticket ride is driven on its pool's `Pool.rideSeed`, a pay-per-ride order on its tier's seed of the UTC day (`ride.DailySeed`); free rides draw their own.
- Money (legacy, `PAYMENT_MODE=transfer`): one global weekly round, a `Payment` row per paid entry, floored lamport shares – .
- **Weekly skill contest** (draft, needs legal review; `docs/prize/SPEC.md`, `docs/prize/OFFICIAL-RULES.md`): operator-funded USDC, not the ticket vault and not TEN4. Variant B is 2 free + 5 paid counted starts, three boards, a $300 base plus 40% of the previous week's ticket revenue. The maths is `server/src/domain/prize/`. The Anchor program is unchanged. Nothing in that contest is paid yet.
- **Escrowed pools** (paid tickets; what is not done + open questions + todo: `docs/escrow-open-items.md` – update it when you close or find something): the money is in the Anchor program `programs/freightchain-pools` (each pool its own vault; a pool that misses `minTickets` by `prepDeadline` fails and anyone can refund). The server only MIRRORS pools (the chain wins) and credits tickets from program EVENTS (the confirm fast path, the program-log watcher, `POST /api/chain/webhook`; `(signature, eventIndex)` unique). Every wallet signs AND sends its own transaction (fee + Ticket rent; no gas sponsor, no `/submit`); the crank (`CRANK_SECRET`, `pool:crank`) sends only permissionless steps by the CHAIN clock; the server's only other key is the payout key (`PAYOUT_SECRET`: since program v4 it commits a pool's winners root, records ride attestations and closes a paid pool – the root is public for the review lock and the cold admin can veto it, so it cannot quietly pay itself). Program mode is ticket-only (no pay-per-ride fallback). Lock order player → pool → tickets. Toolchain: `export PATH="$HOME/.cargo/bin:$HOME/.local/share/solana/install/active_release/bin:$HOME/.avm/bin:$PATH"`, `npm run program:build|test`; after a program change `program:idl` → `(cd server && node scripts/vendor-idl.mjs)` → regenerate `server/test/fixtures/chain/pool-program.json`. Deploy only the `solana-verify build` output (`npm run program:verify`, hash pinned in `verifiable-build.hash`). Never touch the global Solana CLI config or `~/.config/solana/id.json`; chain commands always with an explicit `--url devnet`; no deploy or pool creation without the user (it needs their Phantom).

## Detail

- **One road per competition** (`CreateRideHandler`): a ticket ride takes its pool's `Pool.rideSeed` (the server's, drawn once when the pool enters the mirror – `PoolRegistryService` / `pool:register` / `pool:seed` –, never updated: the upsert writes it only on insert; not on chain, not in the pool DTOs); a pay-per-ride order takes its tier's seed of the UTC day it was ORDERED (`DailySeedRepositoryPort.claim`: the day's first order stores its candidate with INSERT … ON CONFLICT DO NOTHING inside the create transaction, a racing first order waits on the `(tier, day)` key and reads the winner – concurrency-tested). Route, start hour, layout and holes follow from the seed, so a pool's (or a day's) riders drive the same ride. The seed is public once the first of them starts (the watch API); a second ticket drives the same road again. Free rides draw a seed each.
- Money: one global weekly round (UTC Mon→Mon); every paid entry (whatever the ride's outcome) is a `Payment` row; shares are floored integer lamports, remainder to fees; the grand prize shown is what has *accrued* – no draw/settlement/payout code yet. Demo wallets (`DEMO_WALLETS`) get paid shifts ÷`DEMO_SCALE` (`timeScale` on the ride; the speed bound is not scaled). This weekly round is now the LEGACY pay-per-ride path (kept as the `PAYMENT_MODE=transfer` fallback).
- **Solana Pay + reference keys.** A pay-per-ride order, a ticket order and a paid donation each get one reference (base58 of 32 random bytes, private key discarded) the first time a transaction is built for it. The reference is a read-only account on the memo instruction (`buy_ticket`'s account list is unchanged). Confirm still takes the desktop signature. Reconcile looks the payment up with `getSignaturesForAddress(reference)` instead of the wallet's last 25 signatures. A phone pays the same transaction through a public transaction request, no session: `GET/POST /api/solana-pay/{rides|orders|donations}/:id` (`POST` body `{ account }`). The lobby QR is `solana:` plus that URL, URL-encoded. CORS for `/api/solana-pay` is `*`; every other route stays on the origin allowlist. Errors stay problem+json and also carry `message` so a wallet can show them; a wallet other than the order's gets 404 `wrong_account` naming the short form of the account the code is for (the Ticket and any refund belong to the signer, so nobody else may pay it). The QR is also a `solana:` link (a tap on a phone opens the wallet). Desktop payments: a Wallet Standard wallet gets the server's wire bytes (`solana:signAndSendTransaction`, chain `solana:devnet`, the account the transaction was built for – `ensureAccount` says plainly when the wallet is on another one); web3.js is loaded only for a legacy injected wallet. Signing in from a phone for a desktop session is not built: solana.com advises against a sign-in transaction, and WalletConnect would be a dependency. Reopening the lobby looks up an unpaid ticket order by its reference. Reloading a watch page looks up a donation order this browser started. A memo the RPC leaves unparsed (the reference account is on it) is still read from the instruction bytes.
- **Escrowed pools (paid tickets)**: a paid tier is sold as TICKETS into an on-chain pool (`programs/freightchain-pools`): the money sits in the pool's program-owned vault; if fewer than `minTickets` are sold by `prepDeadline` the pool fails and anyone can trigger the refunds; a live pool pays the prizes of its committed winners root (`pay_prize`, capped on chain, never before the pool's REVIEW window `payout_at`) and splits the rest to the seed / fee treasuries at close. **Program v4** (pentest WP5, `programs/freightchain-pools` README "v4"; 29 instructions, 27 events, 48 errors; an in-place, settle-first upgrade of `8No42h…` – BUILT, not deployed: devnet runs v3 until the runbook in `docs/program-deploy.md` "v4"; then `migrate_config_v4` once): **winners root** (H5-B / M6) – the payout key (or admin) `commit_winners` a Merkle root over (rank, wallet, lamports) at/after the play deadline (`total <= prize_share`, ≤ 64 ranks, 0 = no winner; refused when its lock would end within a day of the grace end); it pays from `pay_from = max(payout_at, committed_at + max(payout_at − play_deadline, pool.min_review_secs))`; the cold admin `veto_winners` while no rank is paid; then ANYONE `pay_prize(rank, lamports, proof)` each rank once (`paid_mask`); `close_pool` before the 14-day grace only by admin / payout key once every committed rank is paid, after it as before (anyone if a prize was paid, else `expire_pool`); `paused` stops settlement steps only before the grace (`paused_before_grace`). **Floors** in `Config` (admin `set_config`): `min_review_secs` 3600, `min_finish_secs` 10800 (the last call: 3 h for the shifts on the road) – `set_series` / `create_pool` refuse shorter windows (`WindowTooShort`); each pool snapshots `min_review_secs` and the platform fee; `accept_authority` clears the payout key. **Sponsor receipts** (M8): `sponsor` writes a `SponsorReceipt`; a Refunding pool refunds every sponsor (`refund_sponsor`, permissionless – the crank) before it can close (no longer swept to the seed treasury). Account closes: `close_ride_attestation` / `close_attestation` (v3) / `close_sponsor_receipt` once the pool is finished. The v3 parts below, with v4's changes: (1) **road seed on chain** – v3: `create_pool` / `open_next_pool` read the newest SlotHashes entry themselves (the opener could grind it); **v4 (L4): `seal_road`** (permissionless, the crank ~3 s after the open) hashes the FIRST slot ≥ `seal_slot` = the opening slot + 8 (re-armed only if that left the 512-slot window), storing `seed_commitment = SHA-256(pool_id LE u32 ‖ slot hash ‖ slot LE u64)` + `seed_slot` / `seed_slot_hash`; until it is sealed the server serves no ride of the pool (`Pool.awaitsSeal`, 409 `road_not_sealed`) (no caller passes a seed; `Pool.fromChain` derives `rideSeed` from it with `projectRoadSeed`, `domain/road/provable-seed.ts`; the game re-hashes it in the browser, reads the same seal from the pool account over the public RPC and shows ROAD SEALED ✓ on chain in the cab – `client/js/seal.js`, `ui/cab-chain.js`, which also shows the pool's standings and the ride's pledges while driving); (2) **attestations** – v3's per-driver `Attestation` `[b"attestation", pool, driver]` gated `pay_prize`; v4 pays prizes from the winners root and keeps the v3 accounts only for `close_attestation`. **v4 (H4): `RideAttestation` `[b"ride_attestation", pool, ride_id]`** – the verdict on ONE pledged ride: `telemetry_root` (RFC 6962 Merkle root of the ride's batch hashes, `domain/telemetry/telemetry-merkle.ts`), `verified_km`, `status` 0 unverified / 1 verified / 2 flagged – written only by the admin or the payout key (`record_ride_attestation`, Active pools; `AttestationService.attestRide`, floor km, never rounds a ride under 1 km up); `settle_from` = the same review lock from its record (refused if it would end within a day of the grace end); rewritable until a pledge settled on it; it is the SERVER's verdict put on chain, not a proof; (3) **pledges** `[b"pledge", ride_id (uuid, zero-padded to 32 B), sponsor]` – a spectator locks `lamports_per_km × target_km` (`create_pledge`, before the pool's play deadline); `settle_pledge` (permissionless, on THIS ride's verified / flagged `RideAttestation`, from its `settle_from` and `payout_at`) pays `max × min(km, target) / target` to the driver and closes the account (rest + rent → sponsor); a driver wallet that would stay under the rent minimum makes it wait (`DriverBelowRentMin`) until the grace, then the sponsor gets it all; `refund_pledge` (permissionless) gives everything back once the pool failed / was cancelled / closed / is past its grace and THIS ride has no decided attestation of the pledge's driver. Server: `POST /api/pledges` answers the unsigned `create_pledge` (row `pending`), the sponsor's wallet signs AND sends it, `POST /api/pledges/:id/confirm` reads that transaction's PledgeCreated (→ `active`); the payout job attests every pledged RIDE before its commit and again before `close_pool` (also on `no_winners`), then `SyncPledgesHandler` (after every payout pass) follows each open pledge's account history and sends settle / refund with the payout key (rows `settled` / `refunded`, never computed off chain; `abandoned` = never signed, 1 h). UI: the watch page's PLEDGE block on a ticket ride (`client/js/ui/watch-pledges.js`). Not built: any staking yield (v3's `record_yield` was removed before it went live – the always-0 `stakedLamports` / `yieldEarned` columns were dropped by migration `20261026000000`). **The payout job** (`PayPoolsCommand` → `PoolPayoutScheduler` every `PAYOUT_INTERVAL_MS`, CLI `pool:payout [--pool N]`, `PAYOUT_SECRET`, port `PoolPayoutChainPort`, AppModule only): for each active pool past `payout_at` (chain clock) and not on an admin's signed HOLD (`POST /api/admin/pools/:id/hold`, `Pool.hold`), it runs `PoolAttentionService.markPool`, waits while ANY completed ride of the pool is undecided (`waiting_review` – `RideQueryPort.poolUnreviewed`, asked on EVERY pass, also after the plan – pentest M7), plans the VERIFIED top 20 (always verified-only, whatever `VERDICT_ENFORCE` says) into `economy.PoolPayout`, attests every pledged ride, then COMMITS the plan as the winners root (`commit_winners`, `domain/economy/winners-merkle.ts`, leaf index = rank − 1) → `committed` until `pay_from`; a ranking that drifts from the plan stops in `error` – the admin vetoes the committed root (signed on the admin page; `GET` payout transactions builds the commit / veto for the admin's wallet) and, with the root gone and nothing paid, the job plans and commits again (a partly paid plan stays in `error`). From `pay_from` it CLAIMS each prize (planned → sent with its signature, in one statement only while the pool is not on HOLD – `claimSentUnlessHeld`, pentest L11; the HOLD is read again before the pledge attestations and the close) before broadcasting `pay_prize` with its proof, skips a rank the chain already shows paid (anyone may pay it), resolves a crash from the signature, attests pledged rides decided since, then closes the pool; no verified winner = `no_winners` for the admin; `payout-grace` is logged 3 days before the grace ends. Server-owned `Pool.payoutState` / `hold` change only through `savePayout` / `saveHold` (a chain sync never erases them). Public `GET /api/pools/:id/standings` = the winners list (provisional until planned, then paid per rank); `GET /api/pools` adds `finished` (the last settled pools). Server side: `Pool` = the MIRROR of the account (the chain wins; `PoolRegistryService.syncFromChain`), `RideTicket` per wallet per pool (+ `TicketGrant` audit trail, capped at the pool's `maxPerWallet`), `PromoCode` (free tickets of a tier, atomic last redemption), `TicketOrder` (one per purchase; `(signature, eventIndex)` unique = idempotency). `POST /api/rides` on a pooled tier spends one ticket and the ride is driven on the POOL's seed (`Pool.rideSeed`: since v3 projected from the pool's on-chain `seed_commitment` when the pool enters the mirror, or (v4) once `seal_road` has sealed it – a pre-v3 pool without one keeps a seed the server drew –, never updated, not in the pool DTOs; one pool = one road – route, start hour, layout, holes – for all its riders, the next pool a new one) (in `program` mode paid rides are ticket-only). Payments are credited from the program's EVENTS (`SettleChainSignatureCommand` → `TicketSettlementService`), reached three ways: the confirm fast path (the wallet signs AND sends its own transaction – it pays its network fee and the Ticket rent; there is no gas sponsor and no `/submit`), the program-log watcher (`infrastructure/scheduling/program-watcher.ts`, `WATCH_INTERVAL_MS`, AppModule only – the admin CLI boots ApplicationModule without timers) and `POST /api/chain/webhook` (`WEBHOOK_SECRET`; only signatures are read from the body). The server never holds the admin / treasury key. **Devnet phase** (`docs/escrow-open-items.md`, `docs/program-deploy.md`): `server/scripts/devnet.sh` – keys in the main checkout's `deploy/secrets/devnet/`, the local profile `server/.env.devnet` (the server / CLI with `ENV_FILE=.env.devnet`), `check-rpc` (QuickNode devnet), `db`, `server`, `cli`, `admin`, `payout` (`devnet-payout.mjs`), `rehearse` (the localnet scenario with `TARGET=devnet`). Admin CLI with keypair files (no Phantom): `server/scripts/pool-admin.mjs` (show / initialize / create-pool / set-series / open-next-pool / set-payout-authority / set-config (+ the floors) / migrate-config / seal-road / close-pool / sponsor / buy / commit-winners / veto-winners / pay-prize / record-ride-attestation / close-ride-attestation / close-attestation / refund-sponsor / close-sponsor-receipt / create- / settle- / refund-pledge / fail-pool / expire-pool / refund / close-ticket / cancel-pool / propose- / accept-authority, explicit `--url`, mainnet refused). Dev CLI: `pool:seed` (refused in production), `pool:register`, `pool:crank`, `pool:payout`, `promo:create|list|disable`, `tickets:grant`, `verdict:rejudge`, `retention:sweep`. **The pool crank** (`CRANK_SECRET`, fee money only, its own port `PoolCrankChainPort`): `CrankPoolsCommand` first opens each due series' pool (`seriesDue`, `open_next_pool` – the crank pays the new pool's rents), then reads every pool from chain (`Config.pool_count`), judges by the CHAIN clock (`domain/economy/pool-crank.ts` `nextCrankStep`) and sends `fail_pool` (missed goal), `expire_pool` (active, `payout_at` + 14 d, no prize paid), refunds in batches of 8 (tickets via `getProgramAccounts`), `refund_sponsor` per receipt (v4), `seal_road` of a new pool ~3 s after it opened (v4), `close_pool` of a fully refunded pool – each signature settled at once; `PoolCrankScheduler` every `CRANK_INTERVAL_MS` (60 s; 0 = CLI only), AppModule only. It never closes a pool that paid prizes (the payout key closes it after paying). **Program mode is ticket-only**: a paid tier with no live pool is not on sale (`GET /api/tiers` `available: false`, the lobby's NO POOL card, `POST /api/rides` 409) – the legacy pay-per-ride stays for `PAYMENT_MODE=transfer`. A ride counts for its pool only when it ENDED by the pool's play deadline (`Pool.rideWindow`, pentest H6 – every reader: ranking, unreviewed, best verified ride, attestation, pool attention). **No new sales and no new rides after the sale end** (the user's rule, 2026-10-14): the play window after `prepDeadline` – 3 h on the 1 h series (`ride-tier.ts` schedule) – only lets the shifts already on the road finish. So a ticket is sold until `prepDeadline` (the program refuses `buy` after it), spent (when its ride is ORDERED, `POST /api/rides`) only until `Pool.startBy` = `prepDeadline`, or earlier when a shift of the ride's `minSeconds` started then could not end by the play deadline (a window shorter than the shift: 4 h / 8 h, demo pools), and STARTED while it can still reach its line by the deadline at the governor (`canFinishBy`, the lobby → START gap) – `TicketBalanceDto.ridable` / `rideBy` (the last start) say so, the lobby shows "start by" and lists unused tickets of a closed pool as expired, a late order is 409 `rides_closed` (ticket kept), a late START is 409 `rides_closed` and closes the ride (cancelled; its ticket stays in the pot – the decision of 2026-10-14); an unused ticket of a live pool is not refunded (its money stays in that pot). A ticket is `refundable` as soon as its pool missed its goal (the refund transaction bundles `fail_pool`), not only once the pool is refunding.
