# Verified play – detail

Agent reference, moved verbatim out of `AGENTS.md` (which keeps only the map and the hard rules and is loaded into every agent session); an "In short" block, where there is one, is a summary. Read the file for a topic before changing it; keep it current like AGENTS.md ("Maps stay current").

## In short

- **Verified play** (online rides only, thresholds `server/src/domain/verdict/verdict-rules.ts`): `js/telemetry.js` records every input + a 10 Hz sample and uploads hash-chained batches every 15 s (`POST /api/rides/:id/batches`, under the player row lock; the last one flushed before `/end`). The server judges a **completed** shift `verified` / `flagged` / `rejected` in two tiers: (1) fast batch-summary & road checks (`RideVerdict.judge`: chain, governor, no teleports, ends where the ride ended, covers the driven time, gas pressed, human input timing, natural road holes, off-road) and (2) **10 Hz backend replay verification** (`ReplayEngine` + `@freightchain/shared` in `client/shared/`): re-simulates longitudinal physics (`0.05 s` substeps), deterministic PRNG traffic (`mulberry32`, 4-substep swept OBB CCD), and spectator donation events (`live.RideEvent`), persisting `verdict.RideReplay` + `verdict.RideReplayFlag`. **The server's road**: layout + holes are a pure function of seed + trip, rebuilt by `server/src/domain/road` (port of `net/network.js` + `net/obstacles.js` using `@freightchain/shared`), served as the OBSTACLE PLAN (`GET /api/watch/:id/road`); the game (`js/road-plan.js`) and every replay drive over THOSE holes, and each batch is measured against them (`world-facts.ts` → `world-checks.ts`: `obstacle-ignored`, `offroad-ignored`, `accel-without-gas`). Touching the generator, `PATTERNS`, a trip's `road` / `holesFrom`, `FORK`, `HOLES`, the hole roll, the axles / damage rule in `sim/damage.js`, `client/shared/*` or the off-road rule = change the port / shared module in the same commit (`road-drift.spec.ts`, `replay-engine.spec.ts`). Hand-built recordings must take the holes' damage (`recording(…, { road: seed })` in tests, `server/scripts/road-damage.mjs` for API bots). Bump `RULES_VERSION` when tuning. `VERDICT_ENFORCE=false` = shadow mode, the production default (code default `true`). Sample columns are append-only. One-page anti-cheat: `docs/anti-cheat/index.html`; players: `docs/verified-play/index.html` (keep both in step with `verdict-rules.ts`). Skills `verified-play-test`, `ride-audit`.

## Detail

- **Verified play** (online rides only): `js/telemetry.js` records every key / dash-button press + release (wall-clock ms) and a 10 Hz sample of the truck (`CFG.TELEMETRY_*`), uploads hash-chained batches every 15 s (`POST /api/rides/:id/batches`) and flushes the last one before `/end` (`/end` waits ≤ 3 s for it, retries continue for 55 s; input times are the events' own `timeStamp`; a batch the server refuses stops the recording and is kept in `telemetry.refused`); `ui/input.js` and `main.js` call it, a no-op offline (trace identical). The server judges a **completed** shift from that recording – `verified` / `flagged` / `rejected` with reasons (`server/src/domain/verdict`): it validates the recording (chain, governor, no teleports, ends where the ride ended, covers the driven time, gas was pressed), measures how human the input timing is (flag-only, needs ≥ 8 presses), and runs 10 Hz replay verification (`ReplayEngine`). **The road seed of a ticket ride** is its pool's: since program v3 the program itself commits `seed_commitment = SHA-256(pool_id ‖ slot hash ‖ slot)` from the SlotHashes sysvar when the pool opens, and `Pool.fromChain` projects it to the 31-bit `rideSeed` (`projectRoadSeed`, `domain/road/provable-seed.ts`); no caller passes a seed, so neither a player nor the operator picks the road (it is public once the pool opens – the same for every rider). **RFC 6962 Telemetry Merkle Root**: `computeTelemetryMerkleRoot` calculates the cryptographic Merkle tree across all accepted `RideBatch` records (leaves: `SHA256(0x00 || batchHash)`, internal: `SHA256(0x01 || left || right)`), yielding a 32-byte `telemetry_root` stored on `Ride`. **On-chain Attestation PDAs**: before prize settlement, `AttestationService.ensureAttestation` signs and submits `record_attestation` to Anchor v3, creating an on-chain `Attestation` PDA (`[b"attestation", pool.key().as_ref(), driver.as_ref()]`) storing `telemetry_root`, `verified_km`, and `status: u8` (`Verified` / `Flagged`). `pay_prize` strictly mandates matching `Verified` attestation PDA before releasing vault funds. **The server's road** (since rules v3; current rules v4): the layout and its sinkholes are a pure function of the ride seed and its trip (`Ride.trip` – the free levels' trips have their own layout, `road-rules.ts` `TRIP_ROADS`), so the server rebuilds them itself (`server/src/domain/road`: `road-layout.ts` (`new RoadLayout(seed, trip)`) = the generation half of `net/network.js`, `road-plan.ts` = the obstacle plan, the per-chunk roll of `net/obstacles.js`; `test/unit/domain/road/road-drift.spec.ts` runs the game's own modules beside the port on 40 seeds × 60 km, and every trip's layout) and serves the OBSTACLE PLAN at `GET /api/watch/:id/road?from&to` (public once started, ≤ 10 km a request); the game (`js/road-plan.js`, after `/start` answered) and every replay draw and drive over THOSE holes – the local roll is the offline / not-yet-loaded fallback and counts `plan.mismatches`. Every accepted batch is measured against the plan (`domain/telemetry/world-facts.ts`, `summary.world`: each axle's pass over each pit – wheel depth, v and hull before / after –, off-road spells, speed rises with the gas up and no gas bit) and `verdict/world-checks.ts` judges: a wheel ≥ 0.4 m inside a pit at a speed where the game takes ≥ 1 % must lose ≥ 25 % of that hull, else the hole is IGNORED – ≥ 2 ignored holes reject `obstacle-ignored` (1 flags `obstacle-no-impact`; a game with the holes taken out); each batch is measured WITH the tail of the stored batch before it (the client chooses its cuts – a pass across one is still measured), a pass with no sample before the pit even so (batches uploaded out of order) is unmeasured and 2 such holes flag `obstacle-unmeasured`, > 27 s off the road rejects `offroad-ignored` (the game ends the ride at 20 s; in the first / last 205 m of a FORK – its split / merge apron – the server counts 15 m beyond either edge as road, `RoadLayout.forkApron`, as it does not know which of the two roads the truck took), speed gained with the gas pedal up rejects `accel-without-gas` (≥ 2 m/s or 5 steps; fewer flag). Holes spectators paid for sit NEXT TO a chunk's own hole (`placeHole`, never replacing it) and are correlated by `ReplayEngine`. Hand-built recordings must take that damage too (`test/support/recording.ts` `road: seed`, `server/scripts/road-damage.mjs` for the API bots). Audit any stream from the database: the `ride-audit` skill. Only `verified` paid shifts rank on the paid boards; the free boards rank every completed free ride of their level. **Review of paid rides** (`domain/verdict/ride-review.ts`, derived from the verdict, nothing stored): a completed PAID ride is `review` UNDER REVIEW until the checks verify it (ACCEPTED) or an admin decides (ACCEPTED / REJECTED) – flagged, pending, unjudged AND machine-rejected rides stay under review (a machine reject is not final for the player); `review` rides on the ride DTO and the profile's rides (owner only, like the verdict; null for free and unfinished rides). The game's end panel shows `COMPLETED · VERIFIED` for a free ride and `COMPLETED · UNDER REVIEW / ACCEPTED / REJECTED` for a paid one (re-reading the ride every 3 s for ≤ 30 s while under review), the lobby profile the verdict per free ride and the review per paid ride. **Pool-level attention marks** (`domain/verdict/pool-attention.ts`, NOT verdict rules – no `RULES_VERSION`): `PoolAttentionService.markPool(poolId)` (CLI `pool:attention --pool N`; the payout job calls it before paying) appends `pool-distance-outlier` / `pool-shared-ip` / `pool-new-wallet-top3` flag reasons to the verdicts of the pool's top-20 wallets' rides under each rider's player lock – never over an admin decision, idempotent, carried over by every re-judge. Thresholds in `verdict-rules.ts` are loose first guesses – bump `RULES_VERSION` when tuning. `VERDICT_ENFORCE=false` = shadow mode (judged + shown, the boards and the badges ignore it – enforced, a REJECTED recording earns its ride no achievement, `achievements.ts` `badgeRejected`, judged before the badges at `/end`; a ride with no recording at all still counts; `LeaderboardDto.verifiedOnly` says which) – **the production default** (`docker-compose.prod.yml`: `${VERDICT_ENFORCE:-false}`; the code default stays `true` for tests); rides from before verified play have no verdict and rank only in shadow mode. A recording whose last batch never arrived is not a mismatch – the distance the missing seconds explain is allowed; it only costs coverage. The retention sweep keeps never-judged completed shifts; RE-JUDGE refuses (409) once a recording was swept. Recordings older than `TELEMETRY_RETENTION_DAYS` are swept daily at 00:30 UTC (flagged ones kept). A ride may not hold more recording than its wall time allows (`recordingAllowance`: game seconds ≤ wall × 1.05 + 30, seq ≤ wall / 5 + 10). Batch uploads run under the player row lock like judging, so a batch racing `/end` is always judged. A coarse browser clock (≥ 10 ms steps: Firefox resistFingerprinting, Tor) is detected (`scores.human.timerStepMs`) and skips the two checks it would break. **Judging reads summaries, not samples**: every accepted batch stores `summary` (`domain/telemetry/batch-summary.ts`: counts, first / last sample, max speed, the worst step, a fault, the input events) and `RideVerdict.judge` takes `BatchFacts` (`listFactsByRide`); rows from before are summarised from their payload on the fly. A batch the client could not hash (`hash: null`, the next linked to `unhashed-<seq>`) only FLAGS (`unhashed-batch`); a wrong hash still rejects. Each ride may hold ≤ wall seconds × 4 kB + 256 kB of recording (`totalBytes`, refused 400). The sign-in log is pruned after `SIGNIN_RETENTION_DAYS` (180) by the same 00:30 sweep. CLI: `verdict:rejudge [--status unjudged|verified|flagged|rejected|all] [--since DATE] [--limit N] [--dry-run]` (bulk re-judge at the current rules; admin decisions kept, swept recordings skipped, audited), `pool:attention --pool N` and `retention:sweep`. E2e: the `verified-play-test` skill (`server/scripts/e2e-verified-play.mjs`: a person + a bot in Chrome, API-level bots, the CLI); Not built: payouts, a captcha (landing roadmap, LEG 3), per-ride hole positions (the chunk roll is a hash of the chunk index – the seed only decides which chunks are plain road and the lane count; changing it needs a plan version on the ride). The phone's events ride along as `phone:<what>` input codes (`recordPhone`: open / close, zoom, pan, place, recenter, power-on, ready, offroute…) – kept for audits, ignored by the verdict (`PHONE_PREFIX` in telemetry-rules.ts: not an input, not a press, not in the timing statistics).
- **Backend 10 Hz replay verification & event correlation** (`@freightchain/shared` in `client/shared/` + `server/src/domain/verdict/replay-engine.ts`, `traffic-sim.ts`, `ride-replay.entity.ts`): runs at `REPLAY_SIM_HZ = 10` (`dt = 0.1 s`) with `REPLAY_PHYSICS_SUBSTEPS = 2` (`0.05 s` substeps via `stepLongitudinalPhysics` matching `client/js/main.js`) and 4-substep swept continuous collision detection (`checkTruckTrafficSwept` over `[s0, s1]`), matching 60 Hz accuracy at 1/6 the cost (`ReplayEngine.compareSimFrequencies`). Reproduces deterministic traffic from `createTrafficSim` (`mulberry32((seed ^ 0x9e3779b9) >>> 0)`), correlates spectator donation events (`live.RideEvent`: `potholes` / `trench` / `sinkhole` at `applied.s / applied.lat`, `night` / `day` clock switches, unapplied effects), and stores each verification session (`verdict.RideReplay` + normalized red flags `verdict.RideReplayFlag`, linked 1-to-many from `ride.Ride`). Catch codes: `traffic-collision-ignored`, `traffic-damage-ignored`, `donated-obstacle-ignored`, `event-unapplied`, `event-clock-mismatch`, `physics-speed-mismatch`. Exposed via `GET /api/rides/:id/replays`, `GET /api/admin/replays`, and `GET /api/admin/rides/:id` (`replays`), and processed concurrently across multiple sessions via `ReplayQueuePort` (`RedisReplayQueueAdapter` when `REDIS_URL` is set, `MemoryReplayQueueAdapter` fallback), `ReplayVerificationScheduler`, CLI `replay:verify [--ride ID] [--limit N] [--concurrency C]`, and the dedicated `worker` container (`replay:worker [--interval-ms MS] [--limit N] [--concurrency C]`).
- The anti-cheat in one page (the eight layers, every code, threshold and knob; what it does not do): `docs/anti-cheat/index.html` + `style.css` (opens from disk; keep its numbers in step with `verdict-rules.ts` like the explainer) – the whitepaper's chapter 06 is the short form; for players / non-developers: the explainer page `docs/verified-play/index.html` + `style.css` (diagrams, threats, guarantees, limits – keep its numbers in step with `verdict-rules.ts` and `client/js/telemetry.js` when they change).
