# Verified play – detail

Rules v7 adds mandatory traffic frame proof for new starts (`Ride.trafficVersion=1`, stored in PostgreSQL, chosen by the server). `TRAFFIC_PROOF_REQUIRED=true` is the default; `false` starts historical version-0 rides for compatibility tests. The browser records exact pre-contact `[dt, signalClock, s, d, psi, trailerYaw, v, signedVelocity, hull, reverse, branch, postHull]` frames. `client/shared/traffic-proof.js` packs little-endian Float64/base64 without rounding. `trafficProof` is inside the canonical batch hash; old canonical bytes remain identical when the field is absent. Batches cut every 2 game seconds or 500 frames (64 kB proof); the 98,304-byte batch/100 kB HTTP caps remain. Version-1 ride budgets allow 65,536 canonical bytes/wall second and at most wall seconds/0.2 + 10 batches. Sample columns and input bits are unchanged.

`domain/verdict/traffic-proof.ts` checks encoding, finite values, position/time/resource bounds and a continuous frame clock before each geometry call, then runs the shared traffic kernel with the exact frame state and the ride's route, seed, assist and stamped obstacles. Every 10 Hz sample must match a simulated post-contact pose. Missing or incomplete evidence rejects (`traffic-proof-missing`), malformed/discontinuous evidence rejects (`traffic-proof-invalid`), samples diverging from frames reject (`traffic-proof-mismatch`), ignored crashes reject (`traffic-collision-ignored`), missing contact damage rejects (`traffic-damage-ignored`). Client-supplied protocol versions, omitted replay columns, absent display tracks and re-hashing cannot downgrade the server's requirement. A consistent fabricated simulation is still possible; this does not prove a human drove.

Full headless Chrome coverage: `bash .claude/skills/run-tests/e2e.sh traffic` (`server/scripts/e2e-traffic-proof.mjs`), nine cases on a fresh private server build and throwaway database: normal/automatic-finish/slow honest clients verified; an honest head-on collision ends the ride as failed; cars removed (with/without optional sample columns), damage ignored, proof stripped/re-hashed and malformed/re-hashed rejected. Checks actual browser mutations, accepted uploads, intact hash chains, `/end`, persisted `RideReplay` flags, screenshots and page errors. Chrome's first network request completes before the game's API timeout starts; scenarios run sequentially. macOS uses native Metal rendering; other platforms retain the harness's software WebGL default. The actual renderer is recorded with each result. `test/scenarios/traffic-proof.scenarios.ts` repeats protocol/downgrade cases over in-memory and PostgreSQL repositories. Browser reference fixtures remain independent kernel regression evidence.

The traffic script opens a fresh game document per case, keeps one Chrome process active and restarts it when changing country to release GPU resources. It records at most two retries of a transient initial ride-response timeout, only after the API confirms the ride is still `created`. Driving, upload and verdict assertions never retry. `TRAFFIC_CASES` selects a comma-separated subset for reproducing a failure.

Rules v5 adds a shared telemetry safety gate (`domain/telemetry/sample-safety.ts`) before upload summaries and replay geometry. Unsafe uploads return 400 `bad_batch`; unsafe stored payloads terminate replay with a rejecting `bad-sample`, even when a cached summary has no fault. Rows must have 12–16 finite values within the existing ranges. Coarse resource bounds allow at most `1000 + 56 × game seconds` metres from the start, `1000 + 56 × Δt` metres per step, and 10 km cumulative absolute travel per batch including the preceding 30 rows. Batch time bounds the position allowance; replay also caps that allowance by server ride timestamps plus the upload grace. Empty batches preserve the preceding nonempty tail. These bounds limit geometry work; the tighter governor, teleport, time-order and coverage checks still decide driving validity. No stored column or summary format changed.

Agent reference, moved verbatim out of `AGENTS.md` (which keeps only the map and the hard rules and is loaded into every agent session); an "In short" block, where there is one, is a summary. Read the file for a topic before changing it; keep it current like AGENTS.md ("Maps stay current").

## In short

- **Verified play** (online rides only, thresholds `server/src/domain/verdict/verdict-rules.ts`): `js/telemetry.js` records every input + a 10 Hz sample and uploads hash-chained batches every 15 s (`POST /api/rides/:id/batches`, under the player row lock; the last one flushed before `/end`). The server judges a **completed** shift `verified` / `flagged` / `rejected` in two tiers: (1) fast batch-summary & road checks (`RideVerdict.judge`: chain, governor, no teleports, ends where the ride ended, covers the driven time, gas pressed, human input timing, natural road holes, off-road) and (2) **10 Hz backend replay verification** (`ReplayEngine` + `@freightchain/shared` in `client/shared/`): reconstructs longitudinal physics and shared traffic AI (`≤0.05 s` substeps, approximate between recorded poses), and checks spectator donation events (`live.RideEvent`), persisting `verdict.RideReplay` + `verdict.RideReplayFlag`. **The server's road**: layout + holes are a pure function of seed + trip, rebuilt by `server/src/domain/road` (port of `net/network.js` + `net/obstacles.js` using `@freightchain/shared`), served as the OBSTACLE PLAN (`GET /api/watch/:id/road`); the game (`js/road-plan.js`) and every replay drive over THOSE holes, and each batch is measured against them (`world-facts.ts` → `world-checks.ts`: `obstacle-ignored`, `offroad-ignored`, `accel-without-gas`). Touching the generator, `PATTERNS`, a trip's `road` / `holesFrom`, `FORK`, `HOLES`, the hole roll, the axles / damage rule in `sim/damage.js`, `client/shared/*` or the off-road rule = change the port / shared module in the same commit (`road-drift.spec.ts`, `replay-engine.spec.ts`). Hand-built recordings must take the holes' damage (`recording(…, { road: seed })` in tests, `server/scripts/road-damage.mjs` for API bots). Bump `RULES_VERSION` when tuning. `VERDICT_ENFORCE=false` = shadow mode, the production default (code default `true`). Sample columns are append-only. One-page anti-cheat: `docs/anti-cheat/index.html`; players: `docs/verified-play/index.html` (keep both in step with `verdict-rules.ts`). Skills `verified-play-test`, `ride-audit`. One person with many wallets is not checked. The plan (not built) is `docs/roadmap/anti-sybil.md`.

## Detail

- **Verified play** (online rides only): `js/telemetry.js` records every key / dash-button press + release (wall-clock ms) and a 10 Hz sample of the truck (`CFG.TELEMETRY_*`), uploads hash-chained batches every 15 s (`POST /api/rides/:id/batches`) and flushes the last one before `/end` (`/end` waits ≤ 3 s for it, retries continue for 55 s; input times are the events' own `timeStamp`; a batch the server refuses stops the recording and is kept in `telemetry.refused`); `ui/input.js` and `main.js` call it, a no-op offline (trace identical). The server judges a **completed** shift from that recording – `verified` / `flagged` / `rejected` with reasons (`server/src/domain/verdict`): it validates the recording (chain, governor, no teleports, ends where the ride ended, covers the driven time, gas was pressed) and measures how human the input timing is (flag-only, needs ≥ 8 presses), and runs 10 Hz replay verification (`ReplayEngine`). **The road seed of a ticket ride** is its pool's: the program itself writes `seed_commitment = SHA-256(pool_id ‖ slot hash ‖ slot)` from the SlotHashes sysvar and `Pool.fromChain` projects it to the 31-bit `rideSeed` (`projectRoadSeed`, `domain/road/provable-seed.ts`); no caller passes a seed. v3 took the NEWEST entry when the pool opened, so the opener could time (grind) the open; program v4 (audit L4) seals it with the permissionless `seal_road` from the FIRST slot ≥ the opening slot + 8 – a slot that did not exist when the pool was opened, the same entry whoever calls and whenever – so neither a player nor the operator picks the road. Until it is sealed the server serves no ride of the pool (409 `road_not_sealed`); the seed is public once sealed – the same for every rider. (v4 is built, not deployed: devnet pools are still v3-sealed.) **RFC 6962 Telemetry Merkle Root**: `computeTelemetryMerkleRoot` calculates the cryptographic Merkle tree across all accepted `RideBatch` records (leaves: `SHA256(0x00 || batchHash)`, internal: `SHA256(0x01 || left || right)`), yielding a 32-byte `telemetry_root` stored on `Ride`. **On chain** (program v4): prizes are paid from the pool's committed winners root (the payout job's plan over VERIFIED rides only, public for the review lock, vetoable by the admin – `docs/agents/escrow.md`); `pay_prize` itself checks a Merkle proof against that root, not an attestation. For pledges, `AttestationService.attestRide` sends `record_ride_attestation`, a `RideAttestation` PDA (`[b"ride_attestation", pool, ride_id]`) storing that one ride's `telemetry_root`, `verified_km` and `status: u8` (`Verified` / `Flagged` / `Unverified`); `settle_pledge` pays on it after its own review lock. (v3's per-driver `Attestation` PDA that gated `pay_prize` is only closed now.) **The server's road** (since rules v3; current rules v7): the layout and its sinkholes are a pure function of the ride seed and its trip (`Ride.trip` – the free levels' trips have their own layout, `road-rules.ts` `TRIP_ROADS`), so the server rebuilds them itself (`server/src/domain/road`: `road-layout.ts` (`new RoadLayout(seed, trip)`) = the generation half of `net/network.js`, `road-plan.ts` = the obstacle plan, the per-chunk roll of `net/obstacles.js`; `test/unit/domain/road/road-drift.spec.ts` runs the game's own modules beside the port on 40 seeds × 60 km, and every trip's layout) and serves the OBSTACLE PLAN at `GET /api/watch/:id/road?from&to` (public once started, ≤ 10 km a request); the game (`js/road-plan.js`, after `/start` answered) and every replay draw and drive over THOSE holes – the local roll is the offline / not-yet-loaded fallback and counts `plan.mismatches`. Every accepted batch is measured against the plan (`domain/telemetry/world-facts.ts`, `summary.world`: each axle's pass over each pit – wheel depth, v and hull before / after –, off-road spells, speed rises with the gas up and no gas bit) and `verdict/world-checks.ts` judges: a wheel ≥ 0.4 m inside a pit at a speed where the game takes ≥ 1 % must lose ≥ 25 % of that hull, else the hole is IGNORED – ≥ 2 ignored holes reject `obstacle-ignored` (1 flags `obstacle-no-impact`; a game with the holes taken out); each batch is measured WITH the tail of the stored batch before it (the client chooses its cuts – a pass across one is still measured), a pass with no sample before the pit even so (batches uploaded out of order) is unmeasured and 2 such holes flag `obstacle-unmeasured`, > 27 s off the road rejects `offroad-ignored` (the game ends the ride at 20 s; in the first / last 205 m of a FORK – its split / merge apron – the server counts 15 m beyond either edge as road, `RoadLayout.forkApron`, as it does not know which of the two roads the truck took), speed gained with the gas pedal up rejects `accel-without-gas` (≥ 2 m/s or 5 steps; fewer flag). Holes spectators paid for sit NEXT TO a chunk's own hole (`placeHole`, never replacing it) and are correlated by `ReplayEngine`. Hand-built recordings must take that damage too (`test/support/recording.ts` `road: seed`, `server/scripts/road-damage.mjs` for the API bots). Audit any stream from the database: the `ride-audit` skill. Only `verified` paid shifts rank on the paid boards; the free boards rank every completed free ride of their level. **Review of paid rides** (`domain/verdict/ride-review.ts`, derived from the verdict, nothing stored): a completed PAID ride is `review` UNDER REVIEW until the checks verify it (ACCEPTED) or an admin decides (ACCEPTED / REJECTED) – flagged, pending, unjudged AND machine-rejected rides stay under review (a machine reject is not final for the player); `review` rides on the ride DTO and the profile's rides (owner only, like the verdict; null for free and unfinished rides). The game's end panel shows `COMPLETED · VERIFIED` for a free ride and `COMPLETED · UNDER REVIEW / ACCEPTED / REJECTED` for a paid one (re-reading the ride every 3 s for ≤ 30 s while under review), the lobby profile the verdict per free ride and the review per paid ride. **Pool-level attention marks** (`domain/verdict/pool-attention.ts`, NOT verdict rules – no `RULES_VERSION`): `PoolAttentionService.markPool(poolId)` (CLI `pool:attention --pool N`; the payout job calls it before paying) appends `pool-distance-outlier` / `pool-shared-ip` / `pool-new-wallet-top3` flag reasons (and `pool-duplicate-recording` on the LATER of two rides whose recordings hold the same line across the road – ≤ 0.1 m on ≥ 90 % of ≥ 1 km of shared road, from each batch summary's `print`: d every 25 m of s, keyed by the road not the clock – audit H2: the public replay hands out every sample, and a copy re-hashed under another ride id passes every per-recording check; on production recordings the best match between two wallets was 7 %, Oct 14) to the verdicts of the pool's top-20 wallets' rides under each rider's player lock – never over an admin decision, idempotent, carried over by every re-judge. Thresholds in `verdict-rules.ts` are loose first guesses – bump `RULES_VERSION` when tuning. `VERDICT_ENFORCE=false` = shadow mode (judged + shown, the boards and the badges ignore it – enforced, a REJECTED recording earns its ride no achievement, `achievements.ts` `badgeRejected`, judged before the badges at `/end`; a ride with no recording at all still counts; `LeaderboardDto.verifiedOnly` says which) – **the production default** (`docker-compose.prod.yml`: `${VERDICT_ENFORCE:-false}`; the code default stays `true` for tests); rides from before verified play have no verdict and rank only in shadow mode. A recording whose last batch never arrived is not a mismatch – the distance the missing seconds explain is allowed; it only costs coverage. The retention sweep keeps never-judged completed shifts; RE-JUDGE refuses (409) once a recording was swept. Recordings older than `TELEMETRY_RETENTION_DAYS` are swept daily at 00:30 UTC (flagged ones kept). A ride may not hold more recording than its wall time allows (`recordingAllowance`: game seconds ≤ wall × 1.05 + 30, seq ≤ wall / 5 + 10). Batch uploads run under the player row lock like judging, so a batch racing `/end` is always judged. A coarse browser clock (16.7 / 50 / 100 ms steps: Firefox resistFingerprinting, Tor) is detected (`scores.human.timerStepMs`); since rules v4 the timing checks judge on its grid instead of being skipped (the step is read off the events, so a skip was an escape – audit L1). **Judging reads summaries, not samples**: every accepted batch stores `summary` (`domain/telemetry/batch-summary.ts`: counts, first / last sample, max speed, the worst step, a fault, the input events) and `RideVerdict.judge` takes `BatchFacts` (`listFactsByRide`); rows from before are summarised from their payload on the fly. A batch the client could not hash (`hash: null`, the next linked to `unhashed-<seq>`) only FLAGS (`unhashed-batch`); a wrong hash still rejects. Each ride may hold ≤ wall seconds × 4 kB + 256 kB of recording (`totalBytes`, refused 400). **Rules v4 (audit 2026-10, `docs/reviews/audit-2026-10/fix-plan.md` WP1)**: heartbeats – the whole ride ≤ 28 × 1.05 × wall + 50 m, and a beat ≤ 28 × 1.1 × Δt(game) + 10 m (a game clock standing still while s moves fails the ride; reports without `t` keep the wall bounds only); batches are taken IN ORDER (429 `batch_out_of_order` until the one before is stored – the client retries); the summary measures, as OPTIONAL fields (no `SUMMARY_VERSION` bump – it would drop every older batch's road facts), the longest sample gap, Σ Δs / Σ max(v)·Δt (`motion`), the first / last speed and the gas bit's rising edges, and two rows of one instant metres apart are `sample-out-of-order`; the verdict counts recorded time from the samples (≤ count / 10 Hz, ≤ their span) against max(credited seconds, distance at the governor), and rejects `recording-empty`, `sample-gap` (> 1 s), `speed-mismatch` (> 50 m + 1 % ahead), flags `inputs-mismatch` (gas edges > 1.5 × gas presses + 5); batches from before have no opinion on those. Calibrated on production (32 rides, Oct 14: max gap 0.13 s, excess −15…+5 m, edges = presses). Hardened after a red-team pass: the speed in Σ v·Δt is capped at 28 m/s (the game clamps it exactly – a speedometer read at 29.4 bought 5 %); rows repeating one instant record no time (`dupT`); the game clock may not step back at all inside a batch; a row with an absurd value (|s| > 1e7, v < 0 or > 1000, non-finite) is `bad-sample` BEFORE anything is measured (an s of 1e12 looped the road plan for hours); the motion check measures across an EMPTY batch, the upload measures a batch with the tail of the last batch that had samples, and two empty batches in a row are refused (an empty batch at every pit had hidden the holes); `verdict:rejudge` never touches a ride of a pool whose payout plan exists. The server keeps its own hash of every batch (`RideBatch.serverHash`): an unhashed batch's Merkle leaf is `SHA256(0x02 ‖ serverHash)`. The sign-in log is pruned after `SIGNIN_RETENTION_DAYS` (180) by the same 00:30 sweep. CLI: `verdict:rejudge [--status unjudged|verified|flagged|rejected|all] [--since DATE] [--limit N] [--dry-run]` (bulk re-judge at the current rules; admin decisions kept, swept recordings skipped, audited), `pool:attention --pool N` and `retention:sweep`. E2e: the `verified-play-test` skill (`server/scripts/e2e-verified-play.mjs`: a person + a bot in Chrome, API-level bots, the CLI); Not built: payouts, a captcha (landing roadmap, LEG 3), per-ride hole positions (the chunk roll is a hash of the chunk index – the seed only decides which chunks are plain road and the lane count; changing it needs a plan version on the ride). The phone's events ride along as `phone:<what>` input codes (`recordPhone`: open / close, zoom, pan, place, recenter, power-on, ready, offroute…) – kept for audits, ignored by the verdict (`PHONE_PREFIX` in telemetry-rules.ts: not an input, not a press, not in the timing statistics).
- **Backend 10 Hz replay verification & event correlation** (`@freightchain/shared` in `client/shared/` + `server/src/domain/verdict/replay-engine.ts`, `traffic-sim.ts`, `ride-replay.entity.ts`): consumes 10 Hz telemetry using the browser's shared force calculation and full traffic AI. `traffic-sim.ts` adapts `createTrafficSimulation` in `client/shared/traffic-simulation.js`; `road-network.js`, `road-geometry.js` and `route-curvature.js` supply the same world coordinates, including the ride's assigned route and fork choices. Traffic uses `(seed ^ 0x9e3779b9) >>> 0`, with behind/oncoming/cross cars, signals, hole avoidance and full contact responses; no synthetic slow lead car or server-only speed floors. `simulation-config.js` snapshots the consumed browser tunables/trips and is drift-tested. Original browser reference fixtures in `server/test/fixtures/simulation/` cover five routes × three trips at variable frame durations. `ReplayPhysics` carries speed through sustained passive/braking intervals with favorable warm-engine/faded-brake assumptions. **Historical rules v6 / trafficVersion=0:** traffic checks run for every recording, regardless of optional column width or display traffic tracks. A gap longer than 2 s stops traffic reconstruction (the recording-gap checks reject it); duplicate timestamps cannot disable traffic or reset carried speed. Missing frame timing, transient controls, trailer angle and temperature prevent exact replay: traffic discrepancies and `physics-coasting-mismatch` flag for human review, never automatically reject. There is no claimed 60 Hz equivalence or measured 6× speedup; the old comparison copied its collision results and has been removed. The independent acceleration ceiling and existing road/event checks remain. The engine correlates spectator donation events (`live.RideEvent`: `potholes` / `trench` / `sinkhole` at `applied.s / applied.lat`, `night` / `day` clock switches, unapplied effects), and stores each verification session (`verdict.RideReplay` + normalized red flags `verdict.RideReplayFlag`, linked 1-to-many from `ride.Ride`). Catch codes: `traffic-collision-ignored`, `traffic-damage-ignored`, `donated-obstacle-ignored`, `event-unapplied`, `event-clock-mismatch`, `physics-speed-mismatch`, `physics-coasting-mismatch`. Exposed via `GET /api/rides/:id/replays`, `GET /api/admin/replays`, and `GET /api/admin/rides/:id` (`replays`), and processed concurrently across multiple sessions via `ReplayQueuePort` (`RedisReplayQueueAdapter` when `REDIS_URL` is set, `MemoryReplayQueueAdapter` fallback), `ReplayVerificationScheduler`, CLI `replay:verify [--ride ID] [--limit N] [--concurrency C]`, and the dedicated `worker` container (`replay:worker [--interval-ms MS] [--limit N] [--concurrency C]`).
