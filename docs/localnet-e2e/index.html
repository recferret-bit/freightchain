Freight Chain · test harness · npm run test:localnet

Localnet money test

One command starts a private Solana validator with the escrow program loaded as the exact binary a deploy would ship. It boots the real server against it and drives real wallets through every way money moves: buying tickets, sponsoring a pool, riding, refunds, the crank, prizes and closing. After every step it checks each balance to the lamport against the program's own maths. Nothing touches devnet, and every key is thrown away at the end.

Program = the pinned verifiable build All 4 pool endings: settled, failed, expired, grace close Ten riders paid by the program, to the lamport 14/14 instructions · 12/12 events · 24/24 errors ~10 minutes, paced by the deadlines Local only · nothing signed on devnet
01 · Real vs stand-in

What is the real thing, what stands in for it

The test is only worth something if the parts that move money are the production parts. Only what cannot run on a laptop is replaced: the wallet extension, the calendar, and the time a real shift takes.

Real

  • An Agave 4.1.2 solana-test-validator, with the program loaded as an upgradeable program that has its own ProgramData and upgrade authority.
  • The program binary, by its solana-verify executable hash.
  • The NestJS server in PAYMENT_MODE=program: order building, the gas sponsor's co-sign boundary, the watcher, settlement, the crank, payouts.
  • PostgreSQL, a throwaway database migrated like production.
  • The lobby and the game in headless Chrome. The game records the ride and the server judges it as VERIFIED.
  • Transactions signed with ed25519 and sent to the validator. Fees are read from each transaction.

Stand-in

  • Phantom: a 40-line fake wallet injected into the page. It signs with a throwaway key through the same web3.js the lobby loads, and sends to the local RPC.
  • The calendar: a validator clock can't be moved forward, so two "three weeks old" pools are made by the program itself, then only their two deadline fields are moved back (see Two validators).
  • Shift length: DEMO_SCALE=1200 turns a 1-hour ticket ride into 3 seconds of driving.
  • SOL price: fixed at SOL_USD=118, so no price API is called.

03 · Two validators

Making a pool three weeks old

expire_pool and the permissionless close only work 14 days after a pool's play deadline, and a validator's clock can't be moved forward. Restarting with --warp-slot was tried: the slot moves but unix_timestamp does not, and the validator stalls. So the harness makes the old pools in two phases instead.

Two 8h pools are created; three throwaway buyers buy real tickets, one rent paid by the sponsor; after the play deadline the admin pays one real prize. localnet-fixtures.mjsThe Config, both Pools, their vaults and three Tickets, dumped byte for byte. 05 · The run sheet

Eleven steps, in the order money moves

  1. Baked pools registered

    Both are active on chain with their deadlines 16 days back; one has paid a prize. The Config came from phase 1's real initialize.

  2. Three pools created admin

    pool-admin create-pool, then pool:register. Ids follow the baked Config, and each vault holds exactly the 890 880-lamport rent minimum.

  3. Lobby BUY ×2, gasless P1

    The fake Phantom is only asked to sign; the server adds the sponsor and sends. The buyer pays exactly 2 × price, the sponsor pays the fee plus Ticket rent, and rent_payer is the sponsor.

  4. Self-paid buy → pool live P2

    ?selfPaid=1, then sign, send and /confirm. The buyer pays price + fee + rent, to the lamport. Pool A turns Active on chain and on the server.

  5. Sponsor S

    sponsor of 0.03 SOL into A: the vault and Pool.sponsored grow, and the server mirror picks it up through the watcher. C gets 0.02 SOL the same way.

  6. Buys into B and C; a tampered transaction

    Node gasless (/submit) and self-paid buys. One wallet flips a byte of the message it signs: the sponsor boundary answers 400 and nothing reaches the chain.

  7. Three rides in the real game P1 ×2P2

    Each POST /api/rides {tier:'1h'} spends a ticket. The game drives it with human-timed key presses, and the server judges each ride COMPLETED and VERIFIED.

  8. Missed goal, refunded from the lobby P3P4

    Nobody has failed pool B, yet the card already offers CLAIM REFUND. The wallet signs and sends fail_pool + refund. P4 then refunds through the API (no fail_pool needed any more), and a stranger closes the pool.

  9. Ticket-only anyone

    With B gone the 4h tier has no live pool: /api/tiers says not available with no price, the lobby card says NO POOL, and POST /api/rides answers 409.

  10. The crank crank

    A stranger's close of the unpaid baked pool is refused (MustExpire). One pool:crank pass sends exactly six steps: expire, refund and close the baked pool, then fail, refund and close C. Every refund lands on the right wallet, and the sponsor gets back the rent it paid. The crank pays only fees. A second pass sends nothing.

  11. Grace close, then payouts strangeradmin

    A stranger closes the baked pool that paid a prize, with exact legs. After A's play deadline the admin signs in and gets the ranking (P1 first). Each pay_prize lands exactly, the prize cap includes the sponsorship, close_pool is offered only once every rank is paid, and all five legs match. Conservation: tickets + sponsorship = prizes + legs.

06 · The second scenario

Ten riders, one payout

server/scripts/e2e-localnet-payout.mjs runs one pool the way a real week would: ten wallets buy in, ride, get judged, and the program pays the ranked ones. Every finished ride goes through the same player API the game uses (start, heartbeats, hash-chained recordings, end). There is no admin endpoint that writes telemetry: one that let an admin write recordings would let an admin mint winners. So the payout is tested against the real judge, not a fixture.

  1. Pool D: 10 wallets, 11 tickets adminR1–R10

    Three create_pool attempts are refused first: shares that don't add up, a price below the rent minimum, an unfunded treasury. Then pool D (1h, min 10, ≤ 2 per wallet). R1 buys in the lobby in headless Chrome (gasless: the wallet only signs). Four wallets buy gasless through /submit, four self-paid through /confirm, each to the exact lamport. The pool stays OPEN at 9 sold and goes ACTIVE when R8 buys 2. A fan sponsors 0.05 SOL.

  2. The rides bots + Chrome

    R1 drives the real game. The others are API bots, each with its own 10 Hz recording that takes the damage of the server's planned holes and answers the dispatch prompts. Six honest riders and R8's two rides are VERIFIED. R7 crashes, so its ride FAILED and is never judged. R9 uploads one batch without a hash, gets FLAGGED, and the admin ACCEPTS it with a signed review. R10 teleports 500 m and is REJECTED.

  3. The "cron" CLI

    verdict:rejudge --status all re-judges every completed ride from its telemetry: nothing changes, and the admin's decision stays. A pool:crank pass leaves the live pool alone. Before the play deadline the payout API answers 409, and 403 to a rider.

  4. The payout job admin key

    After the deadline, devnet-payout.mjs --yes signs what GET /api/pools/:id/payout builds. The 8 counted wallets are ranked by summed distance, and each gets exactly its poolPayouts share. The crash and the cheater get nothing, and their ticket money stays in the pot. close_pool legs: fee, platform, seed (seed share + unclaimed rounding) and the creator's rent minimum. Conservation holds to the lamport.

  5. Ticket rents back stranger

    close_ticket ×10 by a stranger: the gas sponsor gets back the 6 rents it advanced, each self-paid buyer its own, and every Ticket account is gone.

  6. The next jackpot seed treasury

    The seed treasury sponsors the next 1h pool with exactly pool D's seed leg, and the lobby's 1h card shows it. This is an operator step: nothing in the code moves the seed by itself.

  7. The rest of the program adminanyone

    Pause (buy and create_pool refused), a sold-out pool, an unpaid pool closed by the admin (the whole prize share goes to the seed), cancel_pool with its refunds (a second refund is refused), and the authority handover there and back (the old admin is refused in between). On the way, every program error a validator can reach is provoked once.

07 · 100 %, defined

The coverage gate

  • What counts: every instruction must succeed and every event must be emitted on a real validator. Every error code must be asserted, either on the validator or in the LiteSVM program tests. That is behaviour coverage of the program's interface, not line coverage of the Rust.
  • Two sources: the ledger (each transaction that named the program, decoded by IDL discriminator and through the server's codec) and the refusals. A refused transaction never lands, so the scenarios record each one with its program error. Phase 1's validator is torn down, so the fixtures script scans its ledger before it goes; that is where initialize runs.
  • Result (scripts/localnet-coverage.mjs report): 14/14 instructions and 12/12 events on the validator, 23/24 error codes there. MathOverflow can only be reached from a forged account, so a LiteSVM test forges one: price × tickets, pot + sponsorship, and play deadline + grace each overflow.
  • SCENARIO=all fails when anything is missing. SCENARIO=payout / money print the table without gating.
08 · How lamports are checked

Expected values come from the server's own maths

  • Prize caps, payout amounts and the close legs come from the server's compiled domain code: prizeBound, poolPayouts, closeSplit (server/dist/domain/economy). These are the same functions the program's money table is pinned against.
  • Every network fee is read from its own transaction (getTransaction(sig).meta.fee), never assumed to be 5 000.
  • Balances are read at confirmed before and after each step, and the difference must match exactly: no tolerance, except the sponsor's fee on the lobby buy, whose signature the page doesn't expose.
  • Server state is compared with chain state after every transition: pool status, tickets sold, sponsorship, the ticket balances in /api/me.
gasless buyer        Δ = −price × qty
self-paid buyer      Δ = −(price × qty + fee + Ticket rent 1 496 400)
refund (own rent)    Δ = +price + rent − fee        refund (sponsor's rent)  Δ = +price − fee, sponsor +rent
close (settled)      fee_out + platform + seed (+ unclaimed) + creator rent = vault, vault → 0
close (cancelled)    seed = sponsorship + stray lamports, creator = 890 880
09 · What it found

Gaps the first runs exposed, and what changed

fixed · server

No crank existed: CRANK_SECRET was read and never used, so a failed pool waited for each buyer to claim. Now CrankPoolsCommand (CLI pool:crank, scheduler CRANK_INTERVAL_MS) fails, expires, refunds 8 per transaction and closes, by the chain clock.

fixed · lobby

A missed-goal pool showed "REFUND SOON" with no button until someone failed it. Its tickets are now refundable at once, and the refund transaction bundles fail_pool.

fixed · product

A tier whose pool failed fell back to pay-per-ride ($15 straight into the weekly round) although program mode is ticket-only. Now the tiers API, the lobby and the landing all say there is no pool on sale.

fixed · lobby

An order the wallet never sent showed as "in flight" for up to an hour. It now says the order is unfinished and nothing was charged.

fixed · program

initialize was first-come. It now requires the upgrade authority, checked here on a real upgradeable loader (phase 1).

open · server

Nothing reclaims Ticket rents after a settlement. close_ticket is in the program, but neither the crank nor the server sends it. Each gasless buyer of a settled pool leaves ~0.0015 SOL of the gas sponsor's money locked. The payout scenario reclaims them by hand (pool-admin.mjs close-ticket); the fix is listed in docs/escrow-open-items.md.

10 · Running it

One command

npm run program:verify          # once: the verifiable .so in target/deploy (the run warns if the binary is not the pinned build)
npm run test:localnet           # = bash .claude/skills/localnet-e2e/run.sh
KEEP=1 npm run test:localnet    # keep keys/, ledgers, validator and server logs in the scratch dir
PLAY_A=240 npm run test:localnet  # slower machine: more time before pool A's play deadline
SCENARIO=payout npm run test:localnet   # only the ten-rider scenario (PREP_D / PLAY_D: 150 / 270 s)
  • Needs Docker (the compose PostgreSQL), Chrome, solana-test-validator, server/node_modules, and internet once (web3.js and three.js load from CDNs).
  • Output: one ok / FAIL line per check, then ✓ all money flows verified on the local chain, ✓ ten riders paid by the program… and the coverage table. On failure it prints the server log tail and keeps the scratch dir.
  • Screenshots go to $TMPDIR/fc-localnet-shots: the lobby after the buy, after the refund, and the NO POOL card.
  • Files: .claude/skills/localnet-e2e/run.sh (stack, two phases), server/scripts/localnet-fixtures.mjs (phase 1), server/scripts/e2e-localnet.mjs (scenario 1), server/scripts/e2e-localnet-payout.mjs (ten riders), server/scripts/localnet-coverage.mjs (the gate), server/scripts/pool-admin.mjs (keypair admin CLI).
11 · Not covered

What a green run does not prove

  • A real Phantom: its popups, its own RPC, and whether it ever rewrites a transaction before signing. The fake signs exactly what it is given.
  • Devnet conditions: congestion, dropped transactions, RPC rate limits, and providers that refuse getProgramAccounts, which the crank needs.
  • Several server instances cranking at once. The program makes it safe, a duplicate refund batch fails whole, but this run uses one server.
  • Session keys and deposits (phase 2 of the plan, not built).
  • Automation the product does not have yet: nothing sends close_ticket after a settlement and nothing rolls the seed treasury into the next pool. The scenario performs both by hand and checks the money.
  • The program is not audited. This test shows the server, lobby and program agree; it is not a security review.
