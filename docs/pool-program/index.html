Freight Chain · Solana program reference

freightchain_pools

One Anchor program that runs many prize pools. Each pool owns a vault that holds the ticket money, and its rules are fixed when the pool is created. A pool that misses its minimum refunds every buyer, and anyone can trigger that. A live pool pays the winners on a list that was public on chain through its review – capped, each once – then splits what is left to the treasuries it declared. This page is the contract's spec sheet. For the plain-language version, see the whitepaper, chapter 05.

01 · Accounts

Eight account types and a vault

v2 – the pool day. Each pool has a sale window (to prep_deadline, closed for Open and Active pools alike), a play window (to play_deadline) and a review window (to payout_at): no prize is paid and no Active pool closed before payout_at, by anyone. The admin writes one Series per tier and anyone opens the next pool from it on a fixed grid – the 1 h tier opens one a day (24 h sale, 2 h more rides, 48 h review). A payout key named by the admin may only pay_prize and close_pool. v2 accounts are larger, so v2 deploys under a fresh program id.

v3 and v4. v3 added per-km pledges and the road seed on chain (in-place upgrade). v4, the security review's fixes (in place again, settle-first), replaces "the payout key pays" with a winners list: the payout key or the admin commits a Merkle root of (rank, wallet, lamports) at or after the play deadline (commit_winners); it is public for the review lock, pay_from = max(payout_at, committed_at + max(payout_at − play_deadline, min_review_secs)); the admin can veto_winners before any rank is paid; then anyone pays each rank once with its proof. A pledge settles on the attestation of its own ride; a failed pool refunds every sponsor; the road seed is sealed from a slot after the pool opened (seal_road); Config carries two floors, min_review_secs (1 h) and min_finish_secs (3 h), which create_pool / set_series enforce and each pool snapshots with the platform fee. After the upgrade migrate_config_v4 grows the Config once.

v5, not deployed. The referral leg is gone. set_pool_rules (the admin) sets paid tickets on or off, the split (default 8500 / 500 / 1000), a player-share cap under 5000 bps (default 4740) and an optional ticket ceiling (0 = none). create_pool and open_next_pool snapshot those onto the pool, so a later change does not move an open pool. Ticket lamports above the cap are not in the prize base; at close they go to the seed treasury (ticket_excess). This is a fresh program id: Config 8+167, Series 8+132, Pool 8+362.

Every account is a PDA of this program, so its address follows from its seeds and nobody holds a private key for it. Pool fields other than status and the counters never change after create_pool. The vault's address is never stored; clients derive it.

02 · Pool states

Five states, no way back

Pool.status moves only forward. Every path ends in Settled, where the pot is split, or in Cancelled, where every buyer has been paid back. Once the settle grace has passed, no path needs the admin.

03 · Instructions

Twenty-nine instructions, by who signs

Admin rights come only from config.authority; the payout key (config.payout_authority) may sign commit_winners, record_ride_attestation and the pre-grace close_pool and nothing else – not veto_winners, and since pay_prize is permissionless it cannot pay itself without its list being public through the lock first. pool.authority just records who created the pool, and it gets the vault's rent minimum back at close. Pausing blocks money coming in (create_pool, open_next_pool, buy_ticket, sponsor, create_pledge) and the pre-grace close; it blocks commit_winners, pay_prize, record_ride_attestation and settle_pledge only until payout_at + 14 d. It never blocks refunds, the veto, seal_road or the permissionless closes.

04 · Deadlines

What each stretch of a pool's life allows

A pool has three deadlines fixed at creation (sale end, play deadline, payout time), plus the 14-day SETTLE_GRACE_SECS written into the program. Prizes also wait for the winners list's own lock (pay_from), which never ends before payout_at. An Open pool past its prep deadline is below its minimum by definition, so the only thing left for it is to fail.

05 · Money maths

Floored shares, the fee takes the dust

Ticket money is derived, not stored: the price never changes, so tickets = price_lamports × tickets_sold. All products are computed in u128 and cast back with a check. Release builds keep overflow-checks on.

pot             = price × tickets_sold + sponsored
room            = ⌊sponsored × max_player_share_bps / (10 000 − bps)⌋
counted_tickets = min(price × tickets_sold, room)
ticket_excess   = tickets − counted_tickets
counted_pot     = counted_tickets + sponsored
prize_share     = ⌊counted_pot × prize_bps / 10 000⌋
seed_share      = ⌊counted_pot × seed_bps  / 10 000⌋
fee_share       = counted_pot − prize_share − seed_share
platform        = ⌊fee_share × pool.platform_fee_bps / 10 000⌋
fee_out         = fee_share − platform

close_pool (Active) pays, vault ends at 0:
  fee_treasury      ← fee_out
  platform_treasury ← platform
  seed_treasury     ← vault − rent_min − fee_out − platform
                      (seed share + unclaimed prize + ticket excess + stray)
  pool.authority    ← rent_min

  • The payout cap is the prize share of the counted pot. Sponsorship raises the room for tickets. Ticket lamports above max_player_share_bps (under 5000; default 4740) are not in the prize or the fee; close_pool carries them to the seed treasury and reports ticket_excess.
  • The platform cut is a share of the fee share, the value the pool opened with (copied from Config at creation, so the cut is the one the buyers were shown). It is 0 for the hackathon.
  • A refunded pool gives every sponsor its sponsorship back (refund_sponsor) before it can close. At the close fee and platform get nothing; what is left (stray lamports) goes to the seed treasury.
  • Amounts are in lamports. The example is the v5 default 85 / 5 / 10 (prize / carry / final) with the player cap exactly full, so excess is 0. platform_fee_bps still skims the final leg; set it to 0 when that leg should be the whole 10%. Each new pool snapshots Config.
06 · Rent rules

The vault keeps 890 880 lamports until it closes

The vault is a zero-data system account, so rent_min = Rent::minimum_balance(0) = 890 880 lamports. create_pool puts exactly that much in. From then on, vault lamports = rent_min + escrow. The money in escrow is vault − rent_min, so never show raw vault lamports as the pot.

09 · Verifiable build

The bytes come from this source

The binary is built with solana-verify 0.5.2 inside the Solana Foundation's pinned Docker image for Solana 4.1.2. The image is chosen from [workspace.metadata.cli] in the program's Cargo.toml. Its executable hash (solana-verify's: sha256 of the .so without its trailing zero padding, so not what sha256sum prints) is committed as programs/freightchain-pools/verifiable-build.hash:

47a630e81fbad16c54c09ffb552d94f7cabff8ab66df46815273a14424ae0100
  • That is the pinned v3 build (v3 is on devnet). A clean rebuild from source reproduces the pinned hash (first checked 2026-10-08, two builds from an empty SBF target). v4 changes the bytes, so its pin is renewed (UPDATE_PIN=1) before its deploy.
  • The 154 tests (151 LiteSVM + 3 unit) load exactly this file (target/deploy/freightchain_pools.so), so the tested bytes and the bytes to deploy are the same.
  • cargo clippy -D warnings is clean on the program. cargo audit finds no RustSec vulnerabilities, only six unmaintained or unsound warnings in transitive Solana and Anchor dependencies.
  • On-chain match: after each deploy, solana-verify get-program-hash must print the pinned hash (check.sh onchain).
  • Public "verified" status (OtterSec API): needs the repository public and an upload signed by the upgrade authority. That is the owner's call.
bash .claude/skills/program-check/check.sh          # build in Docker, compare with the pin, tests, clippy, audit
PROGRAM_ID=<id> bash .claude/skills/program-check/check.sh onchain   # read-only: deployed hash vs pin

A local anchor build --arch v0 produces different bytes (host toolchain), so it would never verify. Deploy only the solana-verify build output. Replacing the placeholder program id changes the hash, so update the pin in the same commit.

10 · Limits

What this program does not do yet

  • Not audited, devnet only: v3 runs there, v4 is built and tested but not deployed. The id in declare_id! is the devnet one.
  • The program pays exactly the committed winners list, capped, after it was public for the review lock – it cannot tell a rightful winner from any other wallet. The admin or the payout key decides the list, and a list with no winner lets the pool close with the unpaid prize share and any ticket excess going to the seed treasury. A stolen payout key is contained by the public lock and the admin's veto; a dishonest admin is not. The escape hatches protect against an absent admin.
  • An attestation is the server's verdict that the payout key signs; the program checks the signer, not the drive.
  • The Pool account is never closed, so explorers and the server can still read it after settlement.
  • Session keys, deposits and buy_ticket_with_session (phase 2) are not built.
  • The binary is SBPF v0, because LiteSVM 0.10 cannot load v3. A v3 deploy would need its own verifiable build and its own pin.
