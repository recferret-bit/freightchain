Freight Chain · Solana program reference

freightchain_pools

One Anchor program that runs many prize pools. Each pool owns a vault that holds the ticket money, and its rules are fixed when the pool is created. A pool that misses its minimum refunds every buyer, and anyone can trigger that. A live pool pays capped prizes, then splits what is left to the treasuries it declared. This page is the contract's spec sheet. For the plain-language version, see the whitepaper, chapter 05.

01 · Accounts

Four account types and a vault

v2 – the pool day. Each pool has a sale window (to prep_deadline, closed for Open and Active pools alike), a play window (to play_deadline) and a review window (to payout_at): no prize is paid and no Active pool closed before payout_at, by anyone. The admin writes one Series per tier and anyone opens the next pool from it on a fixed grid – the 1 h tier opens one a day (24 h sale, 2 h more rides, 48 h review). A payout key named by the admin may only pay_prize and close_pool. v2 accounts are larger, so v2 deploys under a fresh program id.

Every account is a PDA of this program, so its address follows from its seeds and nobody holds a private key for it. Pool fields other than status and the counters never change after create_pool. The vault's address is never stored; clients derive it.

02 · Pool states

Five states, no way back

Pool.status moves only forward. Every path ends in Settled, where the pot is split, or in Cancelled, where every buyer has been paid back. Once the settle grace has passed, no path needs the admin.

03 · Instructions

Seventeen instructions, by who signs

Admin rights come only from config.authority; the payout key (config.payout_authority) may sign pay_prize and close_pool and nothing else. pool.authority just records who created the pool, and it gets the vault's rent minimum back at close. Pausing blocks money coming in (create_pool, open_next_pool, buy_ticket, sponsor). It never blocks refunds, prizes or closing.

04 · Deadlines

What each stretch of a pool's life allows

A pool has three deadlines fixed at creation (sale end, play deadline, payout time), plus the 14-day SETTLE_GRACE_SECS written into the program. An Open pool past its prep deadline is below its minimum by definition, so the only thing left for it is to fail.

05 · Money maths

Floored shares, the fee takes the dust

Ticket money is derived, not stored: the price never changes, so tickets = price_lamports × tickets_sold. All products are computed in u128 and cast back with a check. Release builds keep overflow-checks on.

pot         = price × tickets_sold + sponsored
prize_share = ⌊pot × prize_bps / 10 000⌋
seed_share  = ⌊pot × seed_bps  / 10 000⌋
fee_share   = pot − prize_share − seed_share
platform    = ⌊fee_share × config.platform_fee_bps / 10 000⌋
fee_out     = fee_share − platform

close_pool (Active) pays, vault ends at 0:
  fee_treasury      ← fee_out
  platform_treasury ← platform
  seed_treasury     ← vault − rent_min − fee_out − platform
                      (seed share + unclaimed prize + stray lamports)
  pool.authority    ← rent_min

  • The prize cap is recomputed from the current pot. More sponsorship raises it, and it can never exceed what the pool took in.
  • The platform cut is a share of the fee share, read from Config when the pool closes. It is 0 for the hackathon.
  • When a refunded pool closes, fee and platform get nothing. What is left (sponsorship and stray lamports) goes to the seed treasury.
  • Amounts are in lamports. The example uses the proposed 70 / 20 / 10 split; each pool fixes its own.
06 · Rent rules

The vault keeps 890 880 lamports until it closes

The vault is a zero-data system account, so rent_min = Rent::minimum_balance(0) = 890 880 lamports. create_pool puts exactly that much in. From then on, vault lamports = rent_min + escrow. The money in escrow is vault − rent_min, so never show raw vault lamports as the pot.

09 · Verifiable build

The bytes come from this source

The binary is built with solana-verify 0.5.2 inside the Solana Foundation's pinned Docker image for Solana 4.1.2. The image is chosen from [workspace.metadata.cli] in the program's Cargo.toml. Its executable hash (solana-verify's: sha256 of the .so without its trailing zero padding, so not what sha256sum prints) is committed as programs/freightchain-pools/verifiable-build.hash:

27c0cb40f5052c0922cc16bf7b726c6be0d9516bdb68b316fd7987475ba3b65b
  • A clean rebuild from source reproduces this hash (checked 2026-10-08, two builds from an empty SBF target).
  • The 51 tests (49 LiteSVM + 2 unit) load exactly this file (target/deploy/freightchain_pools.so), so the tested bytes and the bytes to deploy are the same.
  • cargo clippy -D warnings is clean on the program. cargo audit finds no RustSec vulnerabilities, only six unmaintained or unsound warnings in transitive Solana and Anchor dependencies.
  • On-chain match: not possible yet, because nothing is deployed. After the deploy, solana-verify get-program-hash must print the same hash.
  • Public "verified" status (OtterSec API): needs the repository public and an upload signed by the upgrade authority. That is the owner's call.
bash .claude/skills/program-check/check.sh          # build in Docker, compare with the pin, tests, clippy, audit
PROGRAM_ID=<id> bash .claude/skills/program-check/check.sh onchain   # read-only: deployed hash vs pin

A local anchor build --arch v0 produces different bytes (host toolchain), so it would never verify. Deploy only the solana-verify build output. Replacing the placeholder program id changes the hash, so update the pin in the same commit.

10 · Limits

What this program does not do yet

  • Not audited, not deployed, devnet only. The id in declare_id! is the devnet one; nothing is deployed yet.
  • The program caps prize payouts but cannot tell a rightful winner from any other wallet. The admin signs each pay_prize, and may close a pool after its play deadline without paying prizes (the prize share then goes to the seed treasury). The escape hatches protect against an absent admin, not a dishonest one.
  • There is no refund_sponsor. Sponsorship of a failed pool goes to the seed treasury at close.
  • The Pool account is never closed, so explorers and the server can still read it after settlement.
  • Session keys, deposits and buy_ticket_with_session (phase 2) are not built.
  • The binary is SBPF v0, because LiteSVM 0.10 cannot load v3. A v3 deploy would need its own verifiable build and its own pin.
