Freight Chain · test harness · npm run test:localnet

Localnet money test

One command starts a private Solana validator with the escrow program loaded as the exact binary a deploy would ship. It boots the real server against it and drives real wallets through every way money moves: buying tickets, sponsoring a pool, riding, refunds, the crank, prizes and closing – and, for program v4, a whole pool day run by the server alone: the crank opens the pools on their slots and seals their roads, and the payout key commits the winners, waits out the review lock and pays them with proofs. After every step it checks each balance to the lamport against the program's own maths. Nothing touches devnet, and every key is thrown away at the end.

Program = the pinned verifiable build All 4 pool endings: settled, failed, expired, grace close Ten riders paid by the program, to the lamport A whole pool day with no admin signature on chain 29/29 instructions · 26/27 events (+1 exempt) · 48/48 errors ~16 minutes, paced by the deadlines Local only · nothing signed on devnet
01 · Real vs stand-in

What is the real thing, what stands in for it

The test is only worth something if the parts that move money are the production parts. Only what cannot run on a laptop is replaced: the wallet extension, the calendar, and the time a real shift takes.

Real

  • An Agave 4.1.2 solana-test-validator, with the program loaded as an upgradeable program that has its own ProgramData and upgrade authority.
  • The program binary, by its solana-verify executable hash.
  • The NestJS server in PAYMENT_MODE=program: order building, the watcher, settlement, the crank (seals each pool's road; on its own schedule in the day), the payout job with the payout key.
  • PostgreSQL, a throwaway database migrated like production.
  • The lobby and the game in headless Chrome. The game records the ride and the server judges it as VERIFIED.
  • Transactions signed with ed25519 and sent to the validator. Fees are read from each transaction.

Stand-in

  • Phantom: a 40-line fake wallet injected into the page. It signs with a throwaway key through the same web3.js the lobby loads, and sends to the local RPC.
  • The calendar: a validator clock can't be moved forward, so two "three weeks old" pools are made by the program itself, then only their three deadline fields are moved back; and the day's series gets a 120-second slot instead of the program's one-hour minimum, edited into its account (see Three validators).
  • Shift length: DEMO_SCALE=1200 turns a 1-hour ticket ride into 3 seconds of driving (phases 1–2); the autonomous day runs at DEMO_SCALE=48 and its API riders drive past 1 km, because a pledge settles on its ride's attestation and a VERIFIED one needs at least 1 whole km.
  • SOL price: fixed at SOL_USD=118, so no price API is called.

03 · Three validators

Making a pool three weeks old, and a day two minutes long

expire_pool and the permissionless close only work 14 days after a pool's payout time (the end of its review window), and a validator's clock can't be moved forward. Restarting with --warp-slot was tried: the slot moves but unix_timestamp does not, and the validator stalls. So the harness makes the old pools in two phases instead.

05 · The run sheet

Eleven steps, in the order money moves

  1. Baked pools registered

    Both are active on chain with their deadlines 16 days back; one has paid a prize. The Config came from phase 1's real initialize, was cut to the v3 layout and is migrated here by the real migrate_config_v4: refused for a stranger, refused with a floor set first, refused the second time, a 60 s pool under the default floors refused (WindowTooShort), then the floors go back to 0.

  2. Three pools created admin

    pool-admin create-pool, then seal_road once the chain is past each pool's seal slot (the server's crank does it in production; no ride is served on an unsealed road), then pool:register. Ids follow the baked Config, and each vault holds exactly the 890 880-lamport rent minimum.

  3. Lobby BUY ×2 P1

    The fake Phantom is asked to sign and send: the wallet pays its own fee. The buyer pays exactly 2 × price + fee + Ticket rent, and rent_payer is the buyer.

  4. Node buy → pool live P2

    Order, payment, then sign, send and /confirm. The buyer pays price + fee + rent, to the lamport. Pool A turns Active on chain and on the server.

  5. Sponsor S

    sponsor of 0.03 SOL into A: the sponsor also pays the SponsorReceipt's rent, the vault and Pool.sponsored grow, and the server mirror picks it up through the watcher. C gets 0.02 SOL the same way.

  6. Buys into B and C; no gasless route

    Node wallets buy, each to the exact lamport (price + fee + rent). POST /api/tickets/orders/:id/submit, the old gasless route, answers 404.

  7. Three rides in the real game P1 ×2P2

    Each POST /api/rides {tier:'1h'} spends a ticket. The game drives it with human-timed key presses, and the server judges each ride COMPLETED and VERIFIED.

  8. Missed goal, refunded from the lobby P3P4

    Nobody has failed pool B, yet the card already offers CLAIM REFUND. The wallet signs and sends fail_pool + refund. P4 then refunds through the API (no fail_pool needed any more), and a stranger closes the pool.

  9. Ticket-only anyone

    With B gone the 4h tier has no live pool. 4h is not on sale, so /api/tiers says not available and onSale: false with no price, the lobby card says SOON, and POST /api/rides answers 409 tier_not_on_sale.

  10. The crank crank

    A stranger's close of the unpaid baked pool is refused (MustExpire). One pool:crank pass sends exactly seven steps: expire, refund and close the baked pool, then fail, refund, refund_sponsor and close C. Every refund lands on the right wallet, and C's sponsor gets back its sponsorship and the receipt's rent (the seed gets nothing). The crank pays only fees. A second pass sends nothing.

  11. Grace close, then payouts strangeradmin

    A stranger closes the baked pool that paid a prize, with exact legs, then its winner's v3 Attestation (close_attestation, rent to the admin). After A's play deadline the admin signs in and gets the ranking (P1 first), signs commit_winners for it (a prize before the root is WinnersNotCommitted, a second root WinnersCommitted), and each rank is then paid with its proof: every pay_prize lands exactly, the prize cap includes the sponsorship, close_pool is offered only once every rank is paid, and all five legs match. Conservation: tickets + sponsorship = prizes + legs. A stranger returns the sponsor's receipt rent (close_sponsor_receipt).

06 · The second scenario

Ten riders, one payout

server/scripts/e2e-localnet-payout.mjs runs one pool the way a real week would: ten wallets buy in, ride, get judged, and the program pays the ranked ones. Every finished ride goes through the same player API the game uses (start, heartbeats, hash-chained recordings, end). There is no admin endpoint that writes telemetry: one that let an admin write recordings would let an admin mint winners. So the payout is tested against the real judge, not a fixture.

  1. Pool D: 10 wallets, 11 tickets adminR1–R10

    Three create_pool attempts are refused first: shares that don't add up, a price below the rent minimum, an unfunded treasury. Then pool D (1h, min 10, ≤ 2 per wallet), sealed. R1 buys in the lobby in headless Chrome (the wallet signs and sends). Eight wallets buy from Node through /confirm, each to the exact lamport. The pool stays OPEN at 9 sold and goes ACTIVE when R8 buys 2. A fan sponsors 0.05 SOL (plus the receipt's rent).

  2. The rides bots + Chrome

    R1 drives the real game. The others are API bots, each with its own 10 Hz recording that weaves across the lane on its own line (identical lines trip the pool's duplicate-recording mark), takes the damage of the server's planned holes and answers the dispatch prompts. Six honest riders and R8's two rides are VERIFIED. R7 crashes, so its ride FAILED and is never judged. R9 uploads one batch without a hash, gets FLAGGED, and the admin ACCEPTS it with a signed review. R10 teleports 500 m and is REJECTED, which the admin confirms with a signed review (a rejected ride waits for a decision too).

  3. The "cron" CLI

    verdict:rejudge --status all re-judges every completed ride from its telemetry: nothing changes, and the admin's decision stays. A pool:crank pass leaves the live pool alone. Before the payout time the payout API answers 409, and 403 to a rider.

  4. Sale end, review window adminanyone

    The program closes the sale at prep_deadline for an active pool too: a buy into D is TooLate and POST /api/tickets answers 409. D has a 20-second review window after its play deadline, which is the lock of the winners root: the payout API answers 409 until the play deadline, then offers commit_winners and no prize.

  5. A wrong root, vetoed admin keyanyone

    The admin first commits a deliberately wrong list (the vault and an empty wallet; a list above the prize share is refused, PrizeExceedsShare). It lands and is public: a stranger's commit_winners is Unauthorized, a second root WinnersCommitted, a pay_prize inside the lock TooEarly, one to the vault AccountMismatch, and after the lock an empty wallet below the rent minimum BelowRentMin and a proof that is not the root's InvalidProof. A stranger's veto_winners is Unauthorized; the admin's (devnet-payout.mjs --veto) strikes the root, and a second veto is WinnersNotCommitted. Late in the run the scenario also seals a pool about 440 slots after its target, the worst case of the SlotHashes walk, and checks it stays under the crank's CU limit.

  6. The admin's payout admin key

    devnet-payout.mjs --yes signs what GET /api/pools/:id/payout builds: the right commit_winners first, then (it waits out the root's lock on the chain clock) one pay_prize per rank, then the close – ten transactions, no prize before the commit, none before its pay_from, no ride attestation because nothing is pledged. The 8 counted wallets are ranked by summed distance, and each gets exactly its poolPayouts share. The crash and the cheater get nothing, and their ticket money stays in the pot. close_pool legs: fee, platform, seed (seed share + unclaimed rounding) and the creator's rent minimum. Conservation holds to the lamport.

  7. Ticket rents back stranger

    close_ticket ×10 by a stranger: every buyer gets its own rent back, and every Ticket account is gone. The fan's SponsorReceipt is closed the same way.

  8. The next seed rollover seed treasury

    The seed treasury sponsors the next 1h pool (sealed by a stranger) with exactly pool D's seed leg, and the lobby's 1h card shows it. This is an operator step: nothing in the code moves the seed by itself.

  9. The rest of the program adminanyone

    Pause (buy and create_pool refused), a sold-out pool, an unpaid pool closed by the admin after a commit_winners of nobody (the whole prize share goes to the seed), cancel_pool with its refunds and its sponsor's refund_sponsor (a second refund is refused; close_pool waits for the sponsor), the finish floor raised so a short pool is WindowTooShort, the REARM pool re-armed and sealed, and the authority handover there and back (the old admin is refused in between). On the way, every program error a validator can reach is provoked once.

06b · The third scenario

The autonomous day

The autonomous day exists so that a pool day needs nobody: after the admin has written a series and named a payout key, the server opens and seals each pool on its slot and pays the winners once the review lock is over, with a key that cannot veto, create or reconfigure anything. server/scripts/e2e-localnet-day.mjs runs that day on its own validator (phase 3) and its own server, whose crank runs on its schedule – the scenario never sends a crank step. The day's grid is 120 s on sale, 45 s more riding, 45 s of review.

  1. Before the slot stranger

    A fresh Config with no payout key and the floors lowered to 0. A hand-sent open_next_pool is TooEarly, the crank has opened nothing, and pool:payout is off and says the program names no payout key.

  2. The admin's last signatures admin

    set_payout_authority names the payout key; a disabled 4h series makes open_next_pool answer SeriesDisabled. The payout key tries create_pool, set_series, propose_authority and cancel_pool: each is Unauthorized.

  3. The crank opens the pool crank

    On its slot, by itself. The pool's creation transaction is the crank's open_next_pool with PoolCreated.from_series = true; the crank paid exactly the Pool rent, the vault's rent minimum and its fee, and is the pool's creator record. Deadlines follow the series' grid, and GET /api/pools lists the pool. A few seconds later the crank's own seal_road lands: the road's commitment, SHA-256 of pool id, slot hash and slot, is recomputed and matches RoadSealed.

  4. Buys and rides R1–R8

    R1 buys in the lobby (the 1h card sells the series pool), R2–R8 from Node, each to the exact lamport; the pool goes live at 4. Seven rides over the player API: five honest and VERIFIED, one with an unhashed batch (FLAGGED), one teleport (REJECTED). R8 takes a ride and never drives it.

  5. The sale ends anyonecrank

    A buy and a sponsorship into the live pool are TooLate, the API answers 409. The crank opens and seals the next slot's pool where this one stopped selling; R9 buys one ticket of four.

  6. The play deadline payout key

    The payout job takes the pool now, inside the review window, and runs the pool-level marks – the top 3 by distance are brand-new wallets (pool-new-wallet-top3); each rider signed in from its own address and drives its own line, so nobody gets pool-shared-ip or a duplicate-recording mark. It waits: waiting_review, nothing committed. A pay_prize with no root is WinnersNotCommitted; the payout key's close_pool is TooEarly and its veto_winners Unauthorized. The public standings are provisional, four rides under review.

  7. Marks, review, hold admin

    The admin puts a signed HOLD on the pool, then decides every ride with a signed review (three accepted, the teleport rejected). The job now says held and not a lamport moves. A signed release; R8 then starts its ride after the play deadline and is answered 409 rides_closed.

  8. The payout key commits payout key

    The first pass after the release writes a RideAttestation for each pledged ride (R1's VERIFIED with its whole km and the recording's Merkle root, R7's FLAGGED with 0 km, none for R8), then commit_winners: six ranks, total equal to the plan, public until pay_from (the commit plus the review lock). No prize in this pass; a pay_prize or close_pool before pay_from is TooEarly, and a pass inside the lock sends nothing.

  9. The payout key pays payout key

    After pay_from, one pool:payout pass: six pay_prize transactions with their proofs, signed and paid for by the payout key, each verified rank exactly its poolPayouts share, nothing to the rejected rider or the one who never drove, the prizes within the share. Then close_pool, also by the payout key: fee, platform and seed legs equal closeSplit, the vault's rent minimum goes back to the crank as the creator. The standings are final, every rank paid with its signature; a second pass pays nothing.

  10. The pledges sponsorpledge job

    A sponsor pledges per km (the wallet signs and sends create_pledge, then /confirm) to R1, R7 and R8. Each settles on its own ride's attestation: R1 earns the rate times its verified km, R7's flagged ride gives everything back, and R8, never driven and with no attestation, is refunded. Refunding a decided pledge is AttestationExists, closing an attestation while pledges are open PledgesOpen. Afterwards a stranger closes both attestations and the payout key gets each rent back.

  11. The missed slot crank

    The next slot's pool ends its sale under its minimum. The crank alone sends seal_road, fail_pool, refund and close_pool; R9 gets the price and its own Ticket rent back, and the pool is cancelled on chain and in the mirror.

07 · 100 %, defined

The coverage gate

  • What counts: every instruction must succeed and every event must be emitted on a real validator. Every error code must be asserted, either on the validator or in the LiteSVM program tests. That is behaviour coverage of the program's interface, not line coverage of the Rust.
  • Two sources: the ledger (each transaction that named the program, decoded by IDL discriminator and through the server's codec) and the refusals. A refused transaction never lands, so the scenarios record each one with its program error. Each validator is torn down before the next starts, so each ledger is scanned before it goes (phase 1 by the fixtures script – initialize and the series' set_series run there –, phases 2 and 3 by run.sh).
  • Result (scripts/localnet-coverage.mjs report, program v4): 29/29 instructions on the validators, 26/27 events plus one exempt, 48/48 error codes (39 on the validators, the rest in LiteSVM, e.g. MathOverflow, which can only be reached from a forged account: price × tickets, pot + sponsorship, and play deadline + grace each overflow). The exempt event is AttestationRecorded: a v3 event kept in the IDL so old transactions still decode, which no v4 instruction emits. The report also prints the largest compute-unit use per instruction: seal_road 6 932–7 162 (16 902 at 443 slots after its target, limit 40 000), pay_prize with 8 ranks 15 143 (22 000), commit_winners 9 268 (15 000), refund_sponsor 13 893 (25 000), record_ride_attestation 15 324 (30 000), settle_pledge 16 708 (25 000); fail_pool / expire_pool measured 5 852, so their limit is 10 000.
  • SCENARIO=all fails when anything is missing (bar the exempt event). SCENARIO=payout / money / day print the table without gating.
08 · How lamports are checked

Expected values come from the server's own maths

  • Prize caps, payout amounts and the close legs come from the server's compiled domain code: prizeBound, poolPayouts, closeSplit (server/dist/domain/economy). These are the same functions the program's money table is pinned against.
  • Every network fee is read from its own transaction (getTransaction(sig).meta.fee), never assumed to be 5 000.
  • Balances are read at confirmed before and after each step, and the difference must match exactly: no tolerance: every fee is read from its own transaction.
  • Server state is compared with chain state after every transition: pool status, tickets sold, sponsorship, the ticket balances in /api/me.
buyer                Δ = −(price × qty + fee + Ticket rent 1 496 400)
refund (own rent)    Δ = +price + rent − fee
close (settled)      fee_out + platform + seed (+ unclaimed) + creator rent = vault, vault → 0
close (cancelled)    seed = sponsorship + stray lamports, creator = 890 880
09 · What it found

Gaps the first runs exposed, and what changed

fixed · server

No crank existed: CRANK_SECRET was read and never used, so a failed pool waited for each buyer to claim. Now CrankPoolsCommand (CLI pool:crank, scheduler CRANK_INTERVAL_MS) fails, expires, refunds 8 per transaction and closes, by the chain clock.

fixed · lobby

A missed-goal pool showed "REFUND SOON" with no button until someone failed it. Its tickets are now refundable at once, and the refund transaction bundles fail_pool.

fixed · product

A tier whose pool failed fell back to pay-per-ride ($15 straight into the weekly round) although program mode is ticket-only. Now the tiers API, the lobby and the landing all say there is no pool on sale.

fixed · lobby

An order the wallet never sent showed as "in flight" for up to an hour. It now says the order is unfinished and nothing was charged.

fixed · program

initialize was first-come. It now requires the upgrade authority, checked here on a real upgradeable loader (phase 1).

checked · v2

The pool day ran on the real program and server without a fix (Oct 11): the crank opened both slots on the grid, the payout job waited for every decision and for the hold, the payout key paid and closed to the lamport. Things the run makes visible: the pool-level marks put every top-3 ride of brand-new wallets under review, so the admin always has a review round before a new pool pays; the admin signs one change at a time (a second challenge replaces the first – the day decides its rides one after another); pool-admin.mjs create-pool read the chain clock twice, so a default payout_at could land a second after the play deadline (fixed: read once).

fixed · harness

The v4 port lost transactions to the validator's ledger limit. The default keeps 10 000 shreds, a twelve-minute phase 2 outgrew it, and the coverage gate saw 48 of 100 instructions. The validators now run with --limit-ledger-size 2000000.

open · server

Nothing reclaims Ticket rents after a settlement. close_ticket is in the program, but neither the crank nor the server sends it. Every buyer of a settled pool leaves ~0.0015 SOL of its own money locked in its Ticket account until someone sends close_ticket. The payout scenario reclaims them by hand (pool-admin.mjs close-ticket); the fix is listed in docs/tech/escrow-open-items.md.

10 · Running it

One command

npm run program:verify          # once: the verifiable .so in target/deploy (the run warns if the binary is not the pinned build)
npm run test:localnet           # = bash .claude/skills/localnet-e2e/run.sh
KEEP=1 npm run test:localnet    # keep keys/, ledgers, validator and server logs in the scratch dir
PLAY_A=240 npm run test:localnet  # slower machine: more time before pool A's play deadline
SCENARIO=payout npm run test:localnet   # only the ten-rider scenario (PREP_D / PLAY_D / REVIEW_D: 150 / 270 / 20 s)
SCENARIO=day npm run test:localnet      # only the autonomous day (phase 1 + phase 3; DAY_SALE / DAY_PLAY / DAY_REVIEW: 120 / 45 / 45 s, DAY_LEAD 75 s)
  • Needs Docker (the compose PostgreSQL), Chrome, solana-test-validator, server/node_modules, and internet once (web3.js and three.js load from CDNs).
  • Output: one ok / FAIL line per check, then ✓ all money flows verified on the local chain, ✓ ten riders paid by the program…, ✓ the autonomous day… and the coverage table. On failure it prints the server log tail and keeps the scratch dir.
  • Screenshots go to $TMPDIR/fc-localnet-shots: the lobby after the buy, after the refund, the SOON card, the ten-rider buy, the next seed rollover, and the day's lobby buy.
  • Files: .claude/skills/localnet-e2e/run.sh (stack, three phases), server/scripts/localnet-fixtures.mjs (phase 1, the series' retime for phase 3, and the Config migration in phase 2), server/scripts/localnet-seal.mjs (waits past a pool's seal slot, then seal_road), server/scripts/e2e-localnet.mjs (scenario 1), server/scripts/e2e-localnet-payout.mjs (ten riders), server/scripts/e2e-localnet-day.mjs (the day), server/scripts/localnet-coverage.mjs (the gate), server/scripts/pool-admin.mjs (keypair admin CLI).
10b · Chaos

The chain misbehaves, several servers work at once

SCENARIO=chaos puts a fault-injecting RPC proxy between the server and the validator (server/scripts/localnet-fault-proxy.mjs: refuse, 429, swallow a send, forward it but lose the answer, delay, or take a whole provider down). The scenario's own balances and clock stay direct, so only the servers it starts see the faults. Two servers share one database; the crank runs from the command line behind a third proxy.

  • One purchase, every path at once: confirm twice, settle on both servers, the webhook on both, both watchers. One ticket, never two.
  • The crank's send path: its first two sends are swallowed (it is told "accepted"), and its ticket read is refused as well. The re-send loop still lands each step once.
  • Who credits what: one server blind and the other without a websocket still credits by polling; with nobody watching nothing is credited, and a restart catches up on its own; a total provider outage does not kill either server.
  • The crank's ticket read refused: the pass reports the pool's refund as failed and still serves the pools after it; with a working fallback RPC the next pass finishes it.
  • The race: three crankers and a stranger on a ten-ticket pool. Identical transactions dedupe, a step that lost is retried by the next pass, every buyer is refunded exactly once and the crank key paid only fees. Every pool is sealed first, and a failed pool's sponsor is refunded by the same pass (refund_sponsor).

It found a real bug on its first run: one refused ticket read stopped the whole crank pass, so pools after it starved. It also showed that the gasless /submit answered an error for a purchase that had landed, which sent the lobby to a second payment for the same order; the gas sponsor and that route were removed the same day, so every wallet now pays its own fee. The crank fix is unit-tested.

What a green run does not prove

  • A real Phantom: its popups, its own RPC, and whether it ever rewrites a transaction before signing. The fake signs exactly what it is given.
  • A real congested cluster. The chaos scenario (SCENARIO=chaos) imitates how it fails: refused calls, 429s, swallowed and lost sends, getProgramAccounts refused. It does not imitate its timing. Only TARGET=devnet does.
  • Rust line coverage. LiteSVM runs the compiled program, so a host-side coverage tool sees none of the handlers.
  • Session keys and deposits (phase 2 of the plan, not built).
  • A real-length day (24 h on sale, 2 h more riding, 48 h review): the day's grid is compressed to 120 / 45 / 45 s by editing the series' slot length in its account, because set_series refuses a sale window under an hour. The grid maths and the review-window rules are the program's own; the hours are not waited out.
  • The payout job on its schedule (PAYOUT_INTERVAL_MS): the day runs the same handler as pool:payout passes, so each state can be asserted. The crank does run on its schedule there.
  • Automation the product does not have yet: nothing sends close_ticket after a settlement and nothing rolls the seed treasury into the next pool. The scenario performs both by hand and checks the money.
  • The program is not audited. This test shows the server, lobby and program agree; it is not a security review.
