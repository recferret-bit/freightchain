# Configuration guide

Everything in Freight Chain that can be configured, where it lives, and what to change for what. The source of truth for server settings is
[`server/src/infrastructure/config/env.schema.ts`](../server/src/infrastructure/config/env.schema.ts) – this page explains it; if they disagree, the schema wins (and fix this page).

## The map

| What | File | Committed? | Used for |
|---|---|---|---|
| Server settings, local dev | `server/.env` (copy of `server/.env.example`) | no / example yes | `npm run server:dev`, Prisma, tests |
| Production settings | `deploy/.env` (copy of `deploy/.env.example`) | no / example yes | `npm run deploy`; uploaded to the server as `/srv/freightchain/.env` |
| Production secrets on disk | `deploy/secrets/` (`treasury.json` keypair, optional `program-deploy.json`) | **never** | generated by `npm run deploy:init`; never uploaded |
| Local database | `docker-compose.yml` (`FREIGHT_POSTGRES_*`) | yes | dev PostgreSQL on `127.0.0.1:15433` |
| Production stack | `deploy/docker-compose.prod.yml` | yes | which env keys reach the app container (see the trap below) |
| Game tunables | `client/js/config.js` (`CFG`) | yes | gameplay numbers: ride length, shake, traffic, climate… |
| Hosts / URLs | `client/js/hosts.js` | yes | derives API / game / site / admin URLs from the page's hostname |
| Verdict thresholds | `server/src/domain/verdict/verdict-rules.ts` (`RULES_VERSION`) | yes | verified-play rules |
| Ride rules mirrored from client | `server/src/domain/rides/ride-rules.ts` | yes | `MAX_SPEED`, `COMPLETE_DIST_K`, route ids – keep equal to the client |
| Solana program | `programs/freightchain-pools/Anchor.toml` | yes | program id, deploy wallet path |
| Landing build | `landing/vite.config.js` | yes | dev proxy to Nest, build output |
| nginx | `deploy/nginx/*.conf.template` | yes | the six hosts in production |
| Claude Code skills | `.claude/skills/*` | yes | read-only prod tooling + the test runner |
| Claude local settings | `.claude/settings.local.json`, `CLAUDE.local.md` | no | per-person |

`.gitignore` blocks `.env` and `.env.*` (except `.env.example`) and `deploy/secrets/`. **Never print or commit values from `deploy/.env`.**

## Two ways to run, two env files

- **Local**: `server/.env`. Only `DATABASE_URL` is required. Everything else has a dev default.
- **Production**: `deploy/.env` holds *both* deploy settings and the app's environment in one file.
  - Keys starting with `DEPLOY_` stay on your machine.
  - Everything else is uploaded as the server's `.env`.
  - `APP_DOMAIN`, `APP_ORIGIN`, `APP_PORT`, `COOKIE_DOMAIN`, `CORS_ORIGINS` are **derived** from `DEPLOY_DOMAIN` (`deploy/scripts/lib.sh` → `app_env`). Don't type them into `deploy/.env`.
  - Values starting with `CHANGE_ME` block the deploy until replaced. `npm run deploy:init` generates the secrets.
  - Before every deploy the production env is validated by the server's own schema in production mode (`deploy/scripts/validate-env.mjs`). It also refuses a non-devnet `SOLANA_RPC` (override for tests only: `ALLOW_NON_DEVNET=1`).

### ⚠ The compose pass-through trap

The app container only receives the keys **listed** in `deploy/docker-compose.prod.yml`. Putting a key in `deploy/.env` uploads it to the server, but if the compose file doesn't list it, the app never sees it and silently uses the default.

Every schema key except `NODE_ENV`, `PORT`, `DATABASE_URL`, `CLIENT_DIR`, `LANDING_DIR` (fixed by the image / compose) is forwarded. Keep it that way.

A new setting therefore touches **four** places: `env.schema.ts`, `server/.env.example`, `deploy/.env.example`, `docker-compose.prod.yml` (+ `deploy/scripts/init-env.mjs` if it is a generated secret).

A runtime knob (how many free rides a new wallet gets, the daily cap) is **not** an env key. It is a row. See Runtime settings.

## Runtime settings

Table `player.GameSetting` (`key` text, `value` integer). The migration seeds the rows. A missing row, or a stored value outside 0..100_000, falls back to the code default in `server/src/domain/settings/game-settings.ts`. Truncating the table does not change the defaults.

| Key | Default | What it does |
|---|---|---|
| `free_on_signup` | 10 | Free rides a **new** wallet starts with. Wallets that already exist are not topped up. |
| `free_rides_daily_max` | 5 | The +1 at 00:00 UTC stops here. A balance already above it (signup, a promo, an admin grant) stays. |

Change one with the signed admin API (`GET /api/admin/settings`, then the challenge and `POST /api/admin/settings`). Bounds are 0..100_000. The same session can add or remove one signed-in wallet's free rides (`POST /api/admin/players/free-rides`). A result below 0 or above 100_000 is refused.

## Server settings (`env.schema.ts`)

**Req** = required where noted. "prod" = `NODE_ENV=production`, which switches on the strict checks.

### Game rules & economy

| Key | Default | Notes |
|---|---|---|
| `FREE_RIDE_SECONDS` | `180` | Free-ride length – the EASY level's (three minutes, two crossroads – `client/js/trips.js`); MEDIUM is × 5⁄3 (5 min), HARD × 5 (15 min) (`ride-trip.ts` `FREE_LEVELS`). | `HB_MIN_INTERVAL_MS` | `1000` | Minimum spacing of ride heartbeats |
| `HB_TIMEOUT_MS` | `150000` | A running ride with no heartbeat this long has lost its tab – it could not resume anyway (its next heartbeat would fail it): it leaves the live feed and the stale-ride sweeper (every min(30 s, timeout / 3)) ends it as *failed · heartbeat lost*. Tests set it low |
| `DEMO_WALLETS` | empty | Comma-separated wallets (or `*`) whose **paid** rides run `DEMO_SCALE`× shorter – for demo videos |
| `DEMO_SCALE` | `60` | |
| `INITIAL_SEED_SOL` | `0` | SOL the very first prize round starts with |
| `VERDICT_ENFORCE` | code `true`, **prod compose `false`** | `false` = shadow mode: rides are judged and shown but boards ignore the verdict |
| `TELEMETRY_RETENTION_DAYS` | `90` | Recordings swept after this; flagged ones kept until reviewed; `0` = forever |
| `SIGNIN_RETENTION_DAYS` | `180` | The sign-in log (wallet, time, IP, browser) is pruned after this, with the telemetry sweep; `0` = forever |
| `CHALLENGE_INTERVAL_SECONDS` | `240` | Verified play: seconds of driving between two challenges (issued on the heartbeat, 20 s window); a short shift gets at most 4; `0` = off. | `CHALLENGE_FREE_RIDES` | `on` (prod compose: `off`) | Challenges on FREE rides too. Production leaves them off: the free run is the one-minute onboarding ride, it ends itself at the line (a prompt still open then is never judged) and the free board ranks every completed run whatever its verdict |

### Live streams (spectators – feature flags)

Enforced by the server (a refused post is `403 live_feature_off`) and sent to the pages per ride (`features` in `GET /api/watch/:id` and the driver's inbox), so the watch panel and the driver's CB show only what is on. How the feature works: `docs/replay-and-donations/index.html`.

| Key | Default | Notes |
|---|---|---|
| `LIVE_CHAT` | `all` | Spectators' chat: `all` rides · `free` = only on free test rides · `off` |
| `LIVE_DONATIONS` | `on` | `off` = no donations at all (tips and effects) |
| `LIVE_FREE_DONATIONS` | code `on`, **prod compose `off`** | `on` = MOCK donations (nothing charged) · `off` = each donation is a real SOL transfer from the spectator to the driver, verified on chain before it counts |
| `LIVE_EFFECTS` | code `all`, **prod compose `free`** | Donations that change the ride (night / day / holes): `all` rides · `free` = only free test rides, never paid ones · `off` = tips only |

### Product analytics

`env.schema.ts` declares these keys. They are listed in `server/.env.example`, `deploy/.env.example`, and `deploy/docker-compose.prod.yml` `app.environment`, because a key missing from compose never reaches the container. Full behaviour: [`docs/analytics/index.html`](analytics/index.html).

| Key | Default | Notes |
|---|---|---|
| `POSTHOG_KEY` | unset | Project token `phc_…`. Empty = capture off. A `phx_…` or any other non-token is logged once and ignored, and does not stop the API. **Never commit or print it.** Tracked examples stay empty. The real value is only in gitignored `server/.env` and `deploy/.env`. |
| `POSTHOG_HOST` | `https://eu.i.posthog.com` | Ingest. Capture posts to `{host}/batch/`. Project 297915 is EU Cloud. The US ingest host accepts the token and the events never appear on the board. |

| `POSTHOG_ENABLED` | off when unset | Global opt-in. Only `1` or `true` may send. Unset, empty, `0`, or `false` stays off even when `POSTHOG_KEY` is a project token. An enum, not a coerced boolean. | `POSTHOG_DISABLED` | unset | Kill switch. `1` or `true` forces capture off even when `POSTHOG_ENABLED` is on. `0`, `false`, or empty does not turn capture on. An enum, not a coerced boolean (`"false"` must not stick the switch on). |

## Deploy-only keys (`deploy/.env`, never reach the app)

`DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PATH` (must be under `/srv`), `DEPLOY_DOMAIN` (bare apex – `ride.`, `api.`, `storybook.`, `whitepaper.`, `admin.` are added), `DEPLOY_LETSENCRYPT_EMAIL`, `DEPLOY_APP_PORT`, `DEPLOY_KEEP_RELEASES` (3), `DEPLOY_KEEP_BACKUPS` (7), `DEPLOY_ADMIN_USER`, `DEPLOY_ADMIN_PASSWORD`.
Also read by the compose file on the server: `POSTGRES_USER`, `POSTGRES_DB`, `POSTGRES_PASSWORD` (hex only), `APP_PORT` (derived), `RELEASE` (set by the deploy).

DNS: six A records (apex, `ride`, `api`, `storybook`, `whitepaper`, `admin`) → `DEPLOY_HOST`. The session cookie is `Secure`, so https only.

## Client settings

- **`client/js/config.js` (`CFG`)** – every gameplay constant, with comments. Deliberate values not to touch without asking: `SHAKE_START 0.45`, `SHAKE_MOVING 0.09`, `SHAKE_RPM 0.315`, `START_ENGINE_OFF true`.
  `RIDE_MIN_SECONDS` is **300 (a test value); production = 1800**. Tuning requests are relative to the current value. Which constant to touch, which mirror must move with it, and the check to run: the `gameplay-balance` skill (`cd client && npm run check`).
- **Hosts** – never hard-code `/api/…` or `/play.html`; use `API_BASE` / `GAME_BASE` / `SITE_BASE` / `STORYBOOK_BASE` / `WHITEPAPER_BASE` / `ADMIN_BASE` from `client/js/hosts.js`. On localhost, an IP or `file://` they are `''` (one origin).
- **Browser `localStorage` keys** (per player, not config you ship): `freightchain.truck` (F2 handling tuning), `freightchain.radio`, `freightchain.assist` (the lobby's ASSIST checkbox), `freightchain.level` (the free level picked in the lobby: 1 EASY · 2 MEDIUM · 3 HARD), `freightchain.admin`. The analytics branch also writes `freightchain.anon` (`anon_<uuid v4>`).
  A stale value is the first suspect for "works in a fresh browser only" – clear them.
- **In-game F2 panel** – live sliders for truck handling. (The route and the time of day are not settings: the server assigns them to each ride.)
- Server rules that mirror the client (`MAX_SPEED`, `COMPLETE_DIST_K`, route ids) live in `server/src/domain/rides/ride-rules.ts` – change both together.

## Other things you can configure

- **Landing** (`landing/`): dev proxy in `vite.config.js`; `LANDING_DIR` on the server; size budget enforced by `landing/test`. The whitepaper (`whitepaper.html`) is the second Vite input of the same build, served by the same `LANDING_DIR`; host `whitepaper.<apex>` comes from `DEPLOY_DOMAIN`, no env key of its own.
- **App icon**: generated – edit `design/icons/build-app-icons.mjs` and rerun, never the PNGs.
- **nginx / certificates**: `deploy/nginx/*.conf.template`, applied by `npm run deploy:setup` (a new host = new template + `setup.sh` + smoke check + `hosts.js` prefix).
- **Anchor program**: `programs/freightchain-pools/Anchor.toml` (program id, `wallet` → `deploy/secrets/program-deploy.json`, gitignored). Building: `npm run program:build`, `program:test`, `program:idl`.
- **Logging**: JSON lines in production, ring buffer of 5000 in memory for the admin page; read with `npm run ops -- logs`.
- **Scheduled jobs** (no env): free-ride refill 00:00 UTC, the retention sweeps (recordings, sign-ins) 00:30 UTC. By hand: `node dist/cli/index.js retention:sweep`; after a verdict-rules change `verdict:rejudge [--status …] [--since DATE] [--dry-run]` judges completed shifts again.

## Checklist: first production deploy

1. `npm run deploy:init` → edit `deploy/.env` (domain, e-mail, host; `ADMIN_WALLETS`; dedicated devnet `SOLANA_RPC`).
2. Six DNS A records → `DEPLOY_HOST`.
3. `npm run deploy -- --dry-run` and read the plan.

## Known drift

- `POSTHOG_*` in the gitignored env files is intentional and the two files differ. Local `server/.env` pins `POSTHOG_ENABLED=0` (the local compose file is Postgres only and must not turn capture on). Production `deploy/.env` sets `POSTHOG_ENABLED=1`, EU host, project 297915, token not tracked. The live site sends when the running image includes this code. Do not point the host at `us.i.posthog.com`. Do not delete the keys to “clean up”. `POSTHOG_DISABLED=1` still wins.
- `deploy/.env.example` omits `CRANK_SECRET` / `PAYOUT_SECRET` / `POSTHOG_KEY` real values on purpose (dummies and an empty token) and does not list `COOKIE_DOMAIN` / `CORS_ORIGINS` / `APP_*` (derived).
